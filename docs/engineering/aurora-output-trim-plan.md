# Aurora: stop generating the unused detail bullets

**Status:** planned 2026-11-01, owner approved · one phase, one PR · backend only

## Why

Aurora evaluation is one Claude call per run (~0.6 runs/day), ~$0.44 per call, ~$7.60 a month.
Almost all of it is output: 27k tokens (Sonnet 4.6) to 40k (Sonnet 5.5) per call, because the prompt
(`ClaudeAuroraInterpreter.SYSTEM_PROMPT`) asks, for each of 120+ locations, for `name`, `stars`, a
`summary` of up to 120 characters and a `detail` of 3–5 ✓/–/✗ bullets, with a budget of
`BASE_RESPONSE_TOKENS` 256 + `TOKENS_PER_LOCATION` 220 per location (`maxTokensFor`).

Nothing displays `detail`. It is returned by `GET /api/aurora/locations`, saved in the alert snapshot
(`AuroraAlertSnapshotStore` L189, L208) and copied into the admin forecast run's `factors`
(`AuroraForecastRunService` L445); no frontend code reads `detail` or `factors`
(reviewed). The per-location `summary` has two readers: the best location's, on one CSS-truncated
line (`MapView.jsx` ~L6573), and **Ask**, which sends every location's summary to its model as
`NightSpot.auroraSummary` (`AskSnapshotBuilder.java:494`, `AskTools.java:2073`,
`AskThreadContext.java:335`, capped at `NIGHT_SUMMARY_CAP = 120`, `AskTools.java:100`). A 90-character
summary fits that cap, and moving the moon note into the summary gives Ask the moon caveat it lacked.
There is no push or email path for aurora (the prompt's "suitable for a push notification" is
leftover wording). DB `summary` column is 500 chars (`AuroraForecastResultEntity.java:62`).
`AuroraGlossService` has its own separate `detail` and is not affected.

Measured sizing: 40k output tokens per Sonnet 5.5 call implies ~163+ locations (ceiling
256 + 220·N + 4096 thinking). The thinking allowance is fixed (`ModelRequestSupport.java:30,154-156`)
and a `max_tokens` stop fails the whole run on every path (interpreter L212, sync `EvaluationServiceImpl`
after L282, batch `BatchResultProcessor.java:538`; salvage never runs on a truncated reply).

Expected: aurora output down ~55–65% (~$4–5 a month), and alerts arrive sooner because a reply a
third the size generates in a third of the time.

## Change (`service/aurora/ClaudeAuroraInterpreter.java`)

- **Prompt:** ask only for `name`, `stars` and `summary`. Remove the `detail` field and its
  description. Move the moon rule "If illumination > 50%, MUST mention moon impact explicitly in the
  detail field" to the summary ("…in the summary"). Cap the summary at 90 characters (the moonrise /
  moonset time rules and the tone guidance still apply to it; 90 leaves room for "forecast tonight
  from 22:00, moonrise 01:10"). Every scoring rule stays word-for-word; the opening paragraph drops
  "and a brief multi-factor detail".
- **Budget:** `TOKENS_PER_LOCATION` 220 → 110. A pretty-printed entry
  `{"name": "<25–45 chars>", "stars": 4, "summary": "<90 chars>"},` is ~160–185 chars ≈ 67–77 tokens
  at ~2.4 chars/token; ~88 if the model overruns the cap to 120 chars (the cap is a prompt
  instruction only; the parser does not cut it). 110 keeps margin because the thinking allowance is
  fixed and a truncated reply fails the run. Keep `BASE_RESPONSE_TOKENS` 256. Update both constants'
  javadoc. Also drop "suitable for a push notification" from the summary line.
- **Parser:** unchanged in behaviour: `node.path("detail").asString("")` already yields `""` when the
  field is absent, so `AuroraForecastScore.detail` becomes `""` for new runs. Keep the record
  component (the snapshot store and `/api/aurora/locations` serialise it; dropping it is a wider
  change with no saving). Note in `AuroraForecastScore`'s javadoc that `detail` is no longer
  generated by Claude (this plan): empty for parsed rows; `fallbackScore` still writes its
  "Score unavailable" line, which can stay.
- **All three senders** take the prompt and budget from this class (verified): batch
  `EvaluationServiceImpl.java:233-242`, sync `:273-282` (both through `ModelRequestSupport.maxTokens`
  and `tune`), and the admin forecast run `AuroraForecastRunService.java:437` via `interpret()`.
- Class javadoc (L39–45): drop "and a multi-factor detail breakdown".

## Tests

- `ClaudeAuroraInterpreterTest`: the system prompt no longer contains `"detail"`; it still contains
  every scoring rule line (assert a few key ones, e.g. the >75% hard cap and the Bortle lines); the
  moon-impact rule now names the summary; `maxTokensFor(n)` = 256 + 110·n; parsing a reply with no
  `detail` gives `detail == ""` and the right stars/summary; parsing an old-shape reply that still
  carries `detail` still works (stars and summary unchanged).
- Literal budgets to update: `ClaudeAuroraInterpreterTest.java:180-181` (4572 → the new value) and
  `EvaluationServiceImplTest.java:712-714` (476 → the new value); compute from 256 + 110·n (+ the
  thinking allowance where the test includes it). `AuroraForecastRunServiceTest` and
  `AuroraResultHandlerTest` need no change.
- No prompt-regression test covers this interpreter (the aurora-named regression tests concern the
  best-bet pick's own `detail`); none is touched.

per call down ~55–65% and no `max_tokens` failures.
