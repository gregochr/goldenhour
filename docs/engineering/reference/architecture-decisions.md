## Key Architecture Decisions

- **A role variant is not personal data (tide Pro gate B1)** — `GET /api/briefing` is shaped by role at the HTTP edge (`BriefingRoleShaper.forLite`, called only from `BriefingController.getBriefing`; the cached briefing and its internal callers, the digest and Ask, keep the full data). The body depends on the role alone, never on the user, so it stays ETag-revalidated: the ETag is hashed from the shaped body, so a LITE GET carrying a PRO validator gets a 200 with the LITE body and the reverse (`HttpCachingIntegrationTest#briefingEtagDoesNotCrossRoles`), with `Cache-Control: private, no-cache`. The client SWR key is already `briefing:${role}`. Same precedent as the Forecast DTO below. The Backend-heavy bullet's claim that every tide fact is on the shared payload is now true for PRO and ADMIN only; LITE's client reads a missing match as unknown (F0).
- **Forecast DTO** — `ForecastController` returns `ForecastEvaluationDto` via `ForecastDtoMapper`. Role-shaped (scores and written why Pro gate S2, `pro-features-gate-plan.md` §6): PRO/ADMIN get the enhanced potentials, `summary` and detail `headline`; LITE, and any caller not positively PRO_USER or ADMIN (`ForecastController.isLiteUser` is fail-closed), gets all of them null on rich rows, sparse cached-only rows and passed sparse slots alike, while `rating` keeps its selection. `basic_*` entity columns are never served. The same role-variant rule shapes `GET /api/briefing/evaluate/scores` (`LocationEvaluationView.forLite`) and the briefing slots (`BriefingSlot.forLite` inside `BriefingRoleShaper`, built on the canonical constructor, never `withClaudeScores`, so a triage or sample-gate `displayVerdict` survives); the ETag is body-derived so the variants never share a validator (`HttpCachingIntegrationTest#scoresEtagDoesNotCrossRoles`). `swrCache` `PREFIX` is `photocast_swr:v3:` so no pre-strip body is painted.
- **⚠️ Two Jackson object graphs, and the API uses the one you are not looking at.** `AppConfig.objectMapper()` is a **Jackson 2** bean (`com.fasterxml.jackson`) injected into ~a dozen services for internal serialisation — `OpenMeteoClient`, `EvaluationViewService` and others. (Not every Jackson 2 user takes the bean: `RunProgressTracker` and `PromptTestService` each build their own `new ObjectMapper()` with `JavaTimeModule`, and the tracker also turns `WRITE_DATES_AS_TIMESTAMPS` off.) But this is Boot 4 / Framework 7, and `@RestController` responses are serialised by an **auto-configured Jackson 3** (`tools.jackson`) `JsonMapper`: there is no `MappingJackson2HttpMessageConverter` in the handler adapter's converter chain at all. 48 files are on Jackson 2, 8 on Jackson 3. Consequence: **`AppConfig.objectMapper()` is not in the HTTP response path**, so its configuration — notably that it never disables `WRITE_DATES_AS_TIMESTAMPS` — cannot affect the API wire format. A review that reads that bean and concludes the API is at risk has read the wrong graph; this has already happened once (an architecture review flagged it, and the fix hunt landed on the wrong mapper). The wire format is pinned by `backend/src/test/java/com/gregochr/goldenhour/controller/JsonDateFormatContractTest.java` (landed in #666), which asserts through the full Spring context precisely because a hand-built mapper in a test would reproduce the same mistake.

- **Backend-heavy** — all calculations on backend. Frontend is a pure render layer. - **Directional cloud sampling** — 3-point cone sampling (azimuth ±15° at 113 km offset, the geometric horizon distance for low cloud) to smooth Open-Meteo grid-cell boundary effects. Falls back to single-point. Prompt rules: solar low cloud >60% = blocked, 40-60% = penalise, <20% = clear. `findBestIndex()` avoids post-sunset/pre-sunrise slots. - **Cloud approach risk** — detects cloud approaching the solar horizon that a single event-time snapshot would miss. Two signals: (1) `SolarCloudTrend` — hourly low cloud at the solar horizon from T-3h to event time; a peak-vs-earliest increase of 20+ pp triggers a `[BUILDING]` label that tells Claude to penalise fiery_sky by 15–30 points. (2) `UpwindCloudSample` — current low cloud at an upwind point along the wind vector vs the model's event-time prediction; if current is much higher, the model may be too optimistic about clearing. `CloudApproachData` record composes both signals into `AtmosphericData`. `ForecastDataAugmentor` assembles the data from Open-Meteo; `PromptBuilder` formats it as a `CLOUD APPROACH RISK:` block in the user message. V51 migration adds persistence columns. - **Cloud inversion scoring** — two rules worth not re-deriving. **Moisture is counted once**: the temp-dew gap and relative humidity are the same measurement (a gap ≤ 1 °C implies RH 92.7–94.2 % across −5 to 25 °C), so scoring both put 6 of 10 points on one reading and made every calm, saturated dawn total 9 before cloud was considered. **STRONG requires evidence, not inference**: an inversion is temperature *rising* with height, so no combination of surface readings alone may reach the band — `InversionScoreCalculator` demands a measured reversal from `temperature_925hPa` (fallback `850hPa`) against `temperature_2m`, and with no profile at all caps at MODERATE rather than claiming or abandoning the call (`ForecastDataAugmentor` logs a WARN so the feature cannot die silently). Low cloud is a **gate**, not a garnish — outside 15–80 % you are either inside the murk or there is no cloud to form a sea, and both used to score STRONG. The prompt states the measured reversal alongside the score because handing Claude a number and asking for it back makes the "evaluation" an echo of the calculator.

- **The honesty filter words a blanked region by WHY, not always "Too unsettled to forecast"** (`docs/engineering/tide-facts-followups-plan.md` §A). "Too unsettled" is true only of weather triage, yet the filter used to stamp it on every zero-coverage region, including every window Gate 4 never scores (all of T+4, T+3 unless SETTLED), travel days and failed runs. On the API path `BriefingHonestyFilter.apply(response, ratio, latestBySlot, clock)` folds the pipeline's own latest non-`SKIPPED_CACHED` disposition per slot plus the horizon into a `CoverageReason` (`CoverageReasons.of`, pure; the table in the plan is its spec): `AWAY` and `NOT_ATTEMPTED` and `FAILED` read `AWAITING` ("Not forecast" / "Not scored at this range" / "Forecast unavailable"), only `STOOD_DOWN` keeps `STAND_DOWN` and "Too unsettled to forecast"; `UNKNOWN` (the record cannot say) reads `AWAITING` "Not scored" (2026-10-21), so the no-lookup overloads, which fold every region to `UNKNOWN`, read `AWAITING` everywhere. T+4 and later is `NOT_ATTEMPTED` unless a slot was submitted/failed or collection errors reach half; from T+0 to T+3 half or more failed (errors count) is `FAILED`, and otherwise a window skipped by stability, triage or a minority of errors is decided by MAJORITY between stability and triage (the collector triages BEFORE Gate 4, so a mix is the common case; a tie goes to `NOT_ATTEMPTED`, because claiming poor weather needs a majority). `UNKNOWN` is the safe default at T+0 to T+3 (no record, a tie, an unparseable category, a renamed location, a failed lookup, a still-in-flight `EVALUATED`) and the old overloads bypass the fold, so a change can only make a region more honest. - **Gated is not unrated (sub-regions plan D6/D8, S3).** When `LitePickShaper` strips the ratings of a location outside a Lite reader's picks it marks the slot, row or entry `gated: true` (and a shaped briefing carries `allowedLocationIds`). A gated location HAS a rating the reader may not see: it must never be counted as unrated, as "insufficient sample" (`hasSpreadSample`, the thin-sample `· N rated`, the client mirrors of `VerdictSampleGate`), as a stand-down, or as "no data", and it never enters the numerator or the denominator of a rated-versus-total figure. The honesty filter and every region verdict stay keyed on the region and are untouched. Surfaces route gated places out of BOTH numbers and say so in words (S5's job on the client; the server's job, stated now, is to mark them). The client never computes gating and never re-derives a stripped verdict or star. Enforcement is server-side only and fails closed (`allowed = everything` only for enforcement off or a caller positively PRO_USER or ADMIN), and shaped bodies are `no-store`. Region- and window-level verdicts, labels and prose stay free for every role (§9 Q5); only per-location, best and mean stars go.
