A scheduled fire measures a user only when `driveTimesCalculatedAt` is null (never measured, or a postcode change discarded it via `saveHome`) or the location roster has grown since that stamp (`DriveTimeRefreshJob.rosterGrewSince`, deliberately its own predicate, decided from one query for the roster's newest `created_at` rather than one per user) — so a location added after everyone's last refresh does not stay unmeasured forever. Everyone else is skipped with no ORS call at all; a quiet night makes zero. `DynamicSchedulerService.triggerNow` (the admin "Run now" button) still measures every enabled user with a home regardless — the deliberate override for the one thing the stamp cannot detect, a location's coordinates being corrected in place — via a new `registerJobTarget(String, Consumer<Boolean>)` overload that tells a job whether it was fired manually; every other job keeps using the plain `Runnable` overload and behaves identically on both routes | ⚠️ **`driveTimesCalculatedAt` means "drive times were stored for the roster read at this instant" — nothing less, and nothing proves roster coverage on its own.** Both writers stamp with the roster-READ instant, taken immediately before `measureForUser`, never a post-measurement one (a location created while routing runs must read newer than the stamp or it is never picked up) — `rosterGrewSince`'s own boundary is inclusive (`created_at` equal to the stamp counts as grown) and widened by `DriveTimeRefreshJob.ROSTER_VISIBILITY_MARGIN` (one hour): `LocationEntity.createdAt` is assigned before the row is saved, so a location's own `created_at` can read earlier than a roster-read stamp that nonetheless missed it, because the row was not yet visible. The margin is deliberately generous against a real gap bounded by one `JpaRepository.save()` call; the bounded cost is one redundant re-measurement per location, on the very next scheduled run, never repeating. `DriveDurationService.measureForUser` distinguishes **two kinds of nothing**, and the two routes treat the second kind DIFFERENTLY, on purpose — see `UserDriveTimeWriter`'s class javadoc for the full outcome table across {rows stored, no answer, confirmed unreachable, home moved} × {manual, scheduled}. **No answer from ORS at all** (unconfigured, rate-limited, an empty/failed response) leaves rows and stamp exactly as they were, on both routes — a stamp must never advance on nothing learned. **Confirmed unreachable** (ORS answered; no valid duration to any location) is different on the manual route only: `UserDriveTimeWriter.clearIfHomeUnchanged` — a new guarded operation using the same compare-and-set shape `storeIfHomeUnchanged` does, on its own dedicated repository method (`AppUserRepository.clearDriveTimesCalculatedAtIfHomeIs`, a literal `SET ... = NULL` rather than `stampDriveTimesIfHomeIs` called with a `null` instant, so the write never depends on how a bound null binds on a given JDBC driver) and `clearForUser`'s row delete — CLEARS the user's rows and sets the stamp to `null` together, because ORS has just confirmed the stored rows are stale, not merely unmeasured; that is the same state `saveHome` already produces on a home move, which the rest of the product already handles (no "Last calculated" line, the reach lens reads the location as unknown). The **scheduled** job deliberately does NOT do this for the same kind of nothing — it runs with nobody watching, so a transient ORS wobble must not silently wipe a user's drive times overnight; both kinds of nothing are failures there, storing nothing. Both used to be able to leave a genuinely broken state (a non-null stamp with zero rows) behind on the manual path: the no-answer case through a now-deleted `UserDriveTimeWriter.stampIfHomeUnchanged`, and the confirmed-unreachable case because `refreshDriveTimes` used to call `storeIfHomeUnchanged` with an empty list, which clears rows AND stamps in one call — and, in between, a since-corrected fix that merged confirmed-unreachable into the no-answer case entirely, which left a user's now-invalidated drive times in place with no way to know they were stale. The manual refresh's 30-minute cooldown for a *failed or cleared* attempt is tracked separately, in `UserSettingsService.pendingDriveTimeAttempts` (an in-memory `ConcurrentHashMap`, reset by a restart — accepted, since it is a rate limit on a single-instance app, not a record anything downstream reads) — it is the ONLY thing enforcing the cooldown after a confirmed-unreachable clear, since the persisted stamp it leaves behind is `null`. A no-answer response reports the user's own unchanged stamp rather than "now"; a confirmed-unreachable response reports `null`. Migration V157 clears `drive_times_calculated_at` for every user an earlier, pre-fix build left stamped with zero `user_drive_time` rows — a state that cannot recur once every writer follows this rule — and `DriveTimeRefreshJob.needsRefresh`'s own javadoc accepts the one residual cost: a user whose home can never be routed anywhere gets no rows, ever, so their null stamp is re-measured on every scheduled run, matching this job's pre-skip-logic behaviour for exactly that user

## Lite sub-region picks and the change rule (sub-regions-plan S2)

A Lite reader holds up to *n* sub-regions (`SUB_REGION` areas): rows in `app_user_sub_region`, plus two
`app_user` columns, `sub_regions_grace_until` (a UK civil date, inclusive) and `sub_regions_changed_at` (a UTC
wall-clock stamp). Both columns are `updatable = false` and written only by the scoped `@Modifying` updates on
`AppUserRepository` (`startSubRegionGraceIfUnset`, `stampSubRegionsChanged`, `stampSubRegionsChangedIfUnlocked`,
`clearSubRegionsChangedAt`, `clearSubRegionsChangedAtForPickersOf`): the *Column-scoped writes* invariant. *n* is
the single `sub_region_policy` row (default 3, 1..24), read through `SubRegionPolicyService` and
edited from Operations → People → Users (the *Lite limit* button in the list header opens it in a dialog); `photocast.sub-regions.grace-days` (7) and `lock-days` (30) are config.
Pro and Admin never pick: `GET` says `NOT_APPLICABLE`, `PUT` is 403, and picks a demoted-from-Lite Pro still holds
are kept, unused. `photocast.sub-regions.enforce` is only *reported* by S2; nothing is shaped by it until S3.

**The rule** (`UserSubRegionService`, `Clock`-injected, UK civil dates only via `ForecastHorizon.today` /
`civilDate`; `LocalDateTime.now(clock)` for stamps):

- *First choice* (no picks): always allowed; sets `graceUntil = today + grace-days - 1` if it is null; stamps.
- *During grace* (`today <= graceUntil`): any change is allowed and stamps.
- *After grace*: an add-only change under the limit is allowed and stamps nothing; a change that removes a pick
  needs `today >= nextChangeOn = max(graceUntil + 1, changedOn + lock-days)` and stamps.
- An identical set is a 200 no-op. A reader over a lowered limit is flagged `overLimit` and may submit a
  removals-only change without a lock (it stamps nothing); a swap is still locked.
- An admin deleting a sub-region (`AreaService.delete`) clears that area's pickers' `sub_regions_changed_at`
  and deletes the picks, so the re-pick is free.
- Admin tools (`/api/users/{id}/sub-regions`) set picks past the rule (clearing the stamp, leaving the grace end)
  and lift a lock.

**Concurrency.** The lock check and its stamp are one conditional `UPDATE ... WHERE id = :id AND
(sub_regions_changed_at IS NULL OR sub_regions_changed_at < :cutoff)` whose row count is the answer; it runs in
the same transaction as the pick delete and insert, so 0 rows (a lost race) rolls the change back and answers
409 `SUB_REGIONS_LOCKED`. The `:cutoff` is `ForecastHorizon.ukDayStartUtc(today - lock-days + 1)`, so the SQL
agrees with the Java civil-date comparison across a BST midnight. The pick limit is validated before the rule.

**Not in S2.** The registration step (after `HOME`, skipped when `status` is `NOT_APPLICABLE` or `enforced` is
false) and the Settings picker are S4; response shaping by the picks is S3.

**Health status (frontend)**: `HealthStatusProvider` (`context/HealthStatusContext.jsx`, inside `RewindGate`) owns `useHealthStatus` and the deferred (after-first-paint) `/api/status/stream`, and publishes two contexts: the full value (`checkedAt` included) read only by `HealthStatusPill` (the admin pill), and a bare `isDown` boolean (`useHealthIsDown`) that `AppInner` reads for the down banner and `contentDisabled`. A context consumer re-renders only when its value changes by identity, so the 30 s tick that changes only `checkedAt` re-renders the pill and never `App`. The hook keeps `checkedAt` in its own state and replaces the compared health object only when a field other than `checkedAt` differs (`sameHealth`). Recovery on tab wake, the expired-token session probe (#1312) and the 12 s DOWN grace are unchanged. Pinned by `AppHealthRender.test.jsx` (performance-review-2026-10-plan.md P3c).

## A switched-off region never holds a switched-on location (data-tabs-redesign-plan D3, P4)

The services enforce **no switched-on location in a switched-off region** at every door, each refusing with
`RegionStateConflictException` (HTTP 409, `{error}` carrying a plain sentence the UI shows as is):
`RegionService.setEnabled(id, false)` counts `LocationRepository.countEnabledInRegion` and refuses with
"Turn off its {n} locations first."; `LocationService.setEnabled(id, true)`, `add` and `update` (only when it moves a
switched-on location into a different, switched-off region) refuse with "Turn {region} on first.". Turning a region
**on** is always allowed. `LocationService.resetFailures` of an auto-disabled place (one with a `disabledReason`) in a switched-off region is
refused with the same 409 **before any write**, so the reason, counters and Needs-attention signal survive (clearing the
reason alone would silently make it a manually-disabled place). A place with no reason only has its counters cleared.
No other path re-enables a location (`LocationFailureService` only switches places off). `regions.enabled` is
`updatable = false` and written only by `RegionRepository.updateEnabled` (the *Column-scoped writes* invariant), so a
rename or base save cannot write a stale value back over a concurrent turn-on; `setEnabled` to the state a region is already in
is a no-op, never a 409. No migration (`updatable = false` is a JPA mapping only):
existing half-off data is left as is. The checks are check-then-write, not atomic against a concurrent toggle.

### Scheduler fire log (scheduler-redesign-plan.md S1; backend only so far)

`DynamicSchedulerService.wrapTarget` records **every fire** of a scheduled job in `scheduler_fire_log` (V215): a `RUNNING` insert at the start, one scoped `UPDATE` at the end (`completed_at`, `status`, `summary`, `pipeline_run_id`; every other column is `updatable = false`). `status` is `RUNNING | SUCCEEDED | PARTIAL | FAILED | SKIPPED` (`MISSED` will be served, never stored); `trigger` is `SCHEDULED` (an installed schedule), `MANUAL` (`triggerNow`) or `CATCH_UP` (a solar job's startup catch-up). The target still receives `manual == (trigger == MANUAL)`.

- **Reporting**: a job tells the wrapper what its fire amounted to with `SchedulerFireOutcome.report(status, summary)` and `linkPipelineRun(id)`, backed by a JDK 25 `ScopedValue` bound for the job body only (last report wins; no fire bound = a DEBUG no-op; work on other threads cannot report). Nothing reported means `SUCCEEDED`, no summary. S1 shipped the mechanism; S2 (below) made every job report. Tests observe a job's report with `SchedulerFireOutcome.capture(Runnable)`; `count(n, singular, plural)` and `statusFor(failed, total)` keep the wording and the PARTIAL/FAILED rule uniform.
- **Failures**: a throw is logged `FAILED` with a `LogSanitizer`-sanitised, 200-character `ExceptionClass: message` and **re-thrown unchanged**. A logging failure (insert or complete) logs WARN and never stops or fails the job.
- **No lost update**: `last_fire_time` / `last_completion_time` are scoped `@Modifying` updates (`updateLastFireTime`, `updateLastCompletionTime`), not a `findByJobKey` + whole-entity `save`, so a Pause or schedule edit committed mid-fire is no longer reverted when the fire ends. `schedule_changed_at` (read-only on the entity) is stamped by `updateScheduleChangedAt` after a schedule edit, type switch, pause and resume.
- **Orphans**: `initSchedules` first marks `RUNNING` rows with `fired_at < now` as `FAILED` "Interrupted by a restart" (a failure of the sweep never blocks startup).
- **Retention**: 14 days, by the daily `scheduler_fire_log_cleanup` job (03:57 UTC, `SchedulerFireLogCleanupJob`, one bulk `DELETE`).
- **Not logged**: admin routes that run a job body off the scheduler (`startTideRefresh`, the `@Async` cloud-verification backfill) never pass through `wrapTarget`, so they leave no fire-log row.

#### Job catalogue, summary and detail (S3a)

`service/SchedulerJobCatalogue` is a **static** catalogue keyed by `job_key` (not a table, so prod rows stay hand-editable): `alias`, `what`, `why`, a `purpose` tag, the external `services` it calls (empty = database only), `usesClaude`, and the dependency edges. Each edge is declared once (`resultsCollectedBy`, `watches`, `backstoppedBy`, `staggeredBefore`) and its inverse (`collectsResultsFrom`, `watchedBy`, `backstops`, `staggeredAfter`) is derived at class load, so the two directions cannot disagree. The copy is the owner-approved design copy; its one edit is that a `why` never names an editable clock time or interval (it names the rule), because an edited schedule would make it stale. The required config key is not in the catalogue: `configSource` serves it. A job key with no entry serves `catalogue: null`. When a job is added or retired, change its migration and the catalogue together: `SchedulerJobCatalogueSeedTest` (CI, Testcontainers) fails if a `scheduler_job_config` row has no entry or an entry has no row; `SchedulerJobCatalogueAgreementTest` pins the cycle, astro, wildlife, tide, aurora-batch and sky-eval keys to the code that names them.

#### Day view data, schedule preview and UK-time cron edits (S3b)

- **`GET /day`** (`SchedulerDayService`): one UK civil day (`ForecastHorizon.today(clock)`, ±7 days, real injected clock). A job is **repeating** when it is fixed-delay or a cron firing more than `DynamicSchedulerService.REPEATING_FIRES_PER_DAY` (6) times that day (`isRepeating`, status-independent so a paused poller is still a poller; S3a's `nextScheduled` shares the same `exceedsRepeatingThreshold` rule); every other job is **scheduled**. Scheduled jobs list `scheduler_fire_log` rows in the day (one query for all of them) plus the expected slots from `DynamicSchedulerService.firesWithFallback` (the scheduler's own cron/solar arithmetic, with the solar trigger's `Next.fallback` flag). A fire linked to a `pipeline_run` takes its end and status from the run: `RUNNING`->RUNNING, `COMPLETED`->SUCCEEDED, `DEGRADED`->PARTIAL, `FAILED`->FAILED, and a FAILED/PARTIAL run's `failure_reason` replaces the summary.
- **MISSED rule and its caveat**: a slot more than 2 minutes in the past (`MISSED_GRACE_MINUTES`) with no log row within 2 minutes (`MATCH_TOLERANCE_MINUTES`) whose trigger is not `MANUAL` (an admin "Run now" never stands for a slot; a `CATCH_UP` row does, if close enough, otherwise it is listed as its own fire), and strictly after the job's `schedule_changed_at`, is MISSED. There is **no schedule history**: slots are computed from the schedule as it is now, so an edit, type switch, pause or resume hides the earlier part of the day by the `schedule_changed_at` cut-off, and a day older than the 14 day retention shows only what the log still holds. A paused or off-in-config job lists no slots at all, hence no MISSED.
- **Repeating jobs** serve `expectedCount` (fixed delay: elapsed / delay; cron: `CronExpression` stepped uncapped in the job's zone up to now, day end exclusive, so a five-minute cron is 276 on the 23 hour day and 300 on the 25 hour day; counting starts at `schedule_changed_at` when that is later than the day's start; zero for a job that is not ACTIVE), `counts` by status and the newest 50 FAILED/PARTIAL fires. `repeatingTally` is the day's FAILED fires across repeating jobs.
- **Watchdog windows**: `ForecastCycleWatchdog.deadlines(jobKey, date)` is what `check()` compares with the clock. Nightly (sunrise) and intraday (sunset) cycles: the "did not finish" check opens 20 minutes before the event (`FINISH_LEAD_MINUTES`) and closes 60 after (`FINISH_TAIL_MINUTES`), **whatever the job's schedule type** (the event comes from `SolarTriggerFactory.eventInstant`, not from the fire time); the evening refresh serves no event and has `budgetMinutes` (`photocast.pipeline.evening-safety-timeout`); all three have `startGraceMinutes` (30).
- **`POST /jobs/{key}/schedule-preview`** (`SchedulePreviewService`): validates through `DynamicSchedulerService.validateSchedule` (the same validators `updateSchedule` / `switchScheduleType` use) and computes fires on a transient ACTIVE copy of the job, so the answer can never disagree with a save. `CRON` `times` become `0 M H1,H2 * * DOW` and must share one minute value.
- **`PUT /schedule` `timeZone`**: validated by `DynamicSchedulerService.normaliseScheduleZone` (`Europe/London`, or null/`UTC` stored as null), CRON jobs only; written with the cron in one scoped `updateScheduleAndTimeZone` (the entity maps `time_zone` `updatable = false`). A request without the key leaves the zone untouched.
- **Clock**: `calculateNextFireTime`'s fixed-delay branch now reads the injected `Clock` (it used `Instant.now()`).
- Known quirk, surfaced and not changed here: on a day the solar calculation fails, `SolarOffsetTrigger.nextAfter` returns the fallback cron again after the fallback fire has run, so the next day can carry a second fallback fire before its solar one. The day view lists what the scheduler would really do.

#### What each job reports (S2)

Status rules: `SUCCEEDED` = did its job (including "nothing to do"); `SKIPPED` = a deliberate guard (already running, feature flag off, cycle submission dropped); `PARTIAL` = some items failed, others succeeded; `FAILED` = a whole-job failure the job swallowed (a throw is `FAILED` by the wrapper). A job over many items uses `statusFor(failed, total)`. Only the scheduler thread reports: the cycle's wait-and-brief tail and the astro Ask precompute run on other executors and cannot. Summaries carry counts only (no emails, usernames, postcodes).

## Operations → Runs → Model Config (formerly Run Config): measured costs (run-config-accuracy-plan.md)

`components/ModelSelectionView.jsx` holds no price. `GET /api/models` serves `costProfiles` (per tab: runs per day, calls per run, a `measured` figure for each model that ran and an `estimates` figure for each selectable model that did not), `tokenRates` (from `CostProperties`) and `gbpPerUsd` (the newest `job_run.exchange_rate_gbp_per_usd`; absent means the screen shows dollars). `service/RunCostProfileService` builds them from `api_call_log` over the last 30 UK civil days, with a 10-minute memo bypassed under Rewind, and never throws to the controller (a failure serves an empty `costProfiles`, shown as "Cost figures unavailable").

- **Which rows**: Briefing = `BRIEFING` runs' `briefing-best-bet` rows (not the gloss rows); Aurora = `AURORA_EVALUATION` runs plus `au-` batch rows; the batch tabs = `fc-`/`bb-`/`wd-` batch rows whose `forecast_batch.pipeline_run_id` is set (the admin force-submit route is excluded), bucketed by `days_ahead` (0-1 near, 2+ far) in Java. Batch "runs" are pipeline cycles. Per-call figures use succeeded calls only; per-day spend includes every row.
- **Estimates** price the tab's average token mix through `CostCalculator` (batch cache writes at the 1-hour rate); they ignore tokeniser and thinking differences.
- **Not included**: the cache-priming call (`pw-`) logs nothing; a refused or truncated synchronous aurora call is logged at zero cost; admin aurora runs for a chosen night and the aurora gloss log nothing; `BRIEFING_GLOSS` has no tab.

**Drive status: unroutable vs pending (reach-scoped-card-plan R1).** A place OpenRouteService has no route to used
to read as "unknown" and pass every reach tier. Each (origin, location) drive is now MEASURED / PENDING /
UNROUTABLE (`model/DriveStatus`), decided from the origin's stamp (`app_user.drive_times_calculated_at` for a
home, `regions.drives_measured_at` for a base) against `locations.drive_target_changed_at`. A stamp means "fully
measured from this point, as of this instant": it is taken **before** the roster read, written only when ORS
returned a duration slot for every destination (`DriveDurationService` treats a short answer as no answer;
`RegionDriveDurationService` stores a short answer's rows without stamping), and for a region only while the base
is still the one routed from (`RegionDriveTimeWriter.storeIfBaseUnchanged`, a compare-and-set). A coordinate
move in `LocationService.update` bumps `drive_target_changed_at` and deletes the location's drive-time rows, so a
moved location reads PENDING until re-measured and `DriveTimeRefreshJob` (which now reads
`findMaxDriveTargetChangedAt`, not the newest `created_at`) re-measures every home that night. A region base
move (`RegionService.setBase`) also nulls the base's stamp. The admin "Run now" is no longer needed for a
coordinate correction.

**Admin view of unroutable places (reach-scoped-card-plan R1b).** `GET /api/admin/drive-times/unroutable` (ADMIN, read-only,
no-store; `UnroutableLocationService`) counts, per enabled location, how many measured Pro/Admin homes and region bases
read it `UNROUTABLE`, out of how many could judge it (a `PENDING` pair, an origin not yet late enough to judge, is in
neither count), using `DriveStatus.of` and the same `ROSTER_VISIBILITY_MARGIN`. Only locations with at least one
`UNROUTABLE` are listed. The frontend shows it in three admin-only places: a **Needs a drive point** section (count
badge, a link `#manage/locations/{id}` per place) on the Scheduler job panel for `drive_time_refresh`
(`components/scheduler/UnroutableLocationsSection.jsx`), a flag line under the name on the admin Locations list, and a
Drive point section on the location panel above Shooting ("Needs a drive point · no route from 3 of 3 homes, 2 of 4
bases"). All three read `useUnroutableLocations` once on mount; a failed read flags nothing. Pro and Lite never fetch
it (the Operations pane and the Manage tab are withheld from them, and the endpoint answers 403).
