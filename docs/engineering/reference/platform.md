**User settings**: `UserSettingsService` + `UserSettingsController` — home location (postcode via `PostcodesIoClient` geocoding, lat/lon) and per-user drive times | `DriveTimeResolver` abstraction (replaces per-location `drive_duration_minutes`) | `user_drive_time` table (V67) | ⚠️ **The nine settings columns on `app_user` are `updatable = false`** (counted from `AppUserEntity` 2026-10-17) — home postcode, latitude and longitude, local radius, drive-time stamp, map colour scale, map tide mode (`map-mobile-sheet-plan.md` M4), Coming-up last-seen and the postcode-prompt dismissal (`postcode_prompt_dismissed_at`, V181) — and are written only by column-scoped updates on `AppUserRepository`. The credential and authority columns follow the same rule — `password`, `enabled`, `password_change_required`, `role`, `credentials_changed_at` and `credentials_version` — and are written only by `CredentialChangeWriter` (a re-enable alone by `updateEnabled`) and `updateRole`. So `setX()` then `save()` on an existing user writes NONE of them (inserts are unaffected). A whole-entity save wrote every column from whatever copy it held, so overlapping writes lost one another — and the JWT filter's last-active save, made at most hourly from whichever authenticated request comes first, is one such writer. | A drive-time refresh, manual or nightly, stores only while the home is still the one it measured from: `UserDriveTimeWriter.storeIfHomeUnchanged` compare-and-sets the stamp on the measured coordinates, then replaces the rows in the same transaction. Otherwise the manual refresh answers **409** having written nothing (a retry is always allowed, because the move released the cooldown), and the job counts that user as superseded. `saveHome` decides whether the home moved from a `SELECT … FOR UPDATE` read | ⚠️ **Drive times from home are Pro/Admin only on the server (`pro-features-gate-plan.md` D2).** `POST /drive-times/refresh`, `GET /drive-times` and `GET /reach` carry `@PreAuthorize("hasAnyRole('PRO_USER','ADMIN')")` (LITE 403), and `DriveTimeRefreshJob.run` filters its `findAll()` roster in memory to enabled PRO_USER/ADMIN accounts with a home on both routes, the admin "Run now" included (a null role is excluded), so no ORS quota is spent on LITE homes. Saving a home stays open to every role; stored LITE rows are left in place and a promoted account's next run or Refresh press rewrites them | ⚠️ **The nightly `drive_time_refresh` job only re-measures a user who needs it — it no longer re-measures everyone every night.** OpenRouteService is a free-plan call budget shared across every user, and most nights every answer is identical to the one before. A scheduled fire measures a user only when `driveTimesCalculatedAt` is null (never measured, or a postcode change discarded it via `saveHome`) or the location roster has grown since that stamp (`DriveTimeRefreshJob.rosterGrewSince`, deliberately its own predicate, decided from one query for the roster's newest `created_at` rather than one per user) — so a location added after everyone's last refresh does not stay unmeasured forever. Everyone else is skipped with no ORS call at all; a quiet night makes zero. `DynamicSchedulerService.triggerNow` (the admin "Run now" button) still measures every enabled user with a home regardless — the deliberate override for the one thing the stamp cannot detect, a location's coordinates being corrected in place — via a new `registerJobTarget(String, Consumer<Boolean>)` overload that tells a job whether it was fired manually; every other job keeps using the plain `Runnable` overload and behaves identically on both routes | ⚠️ **`driveTimesCalculatedAt` means "drive times were stored for the roster read at this instant" — nothing less, and nothing proves roster coverage on its own.** Both writers stamp with the roster-READ instant, taken immediately before `measureForUser`, never a post-measurement one (a location created while routing runs must read newer than the stamp or it is never picked up) — `rosterGrewSince`'s own boundary is inclusive (`created_at` equal to the stamp counts as grown) and widened by `DriveTimeRefreshJob.ROSTER_VISIBILITY_MARGIN` (one hour): `LocationEntity.createdAt` is assigned before the row is saved, so a location's own `created_at` can read earlier than a roster-read stamp that nonetheless missed it, because the row was not yet visible. The margin is deliberately generous against a real gap bounded by one `JpaRepository.save()` call; the bounded cost is one redundant re-measurement per location, on the very next scheduled run, never repeating. `DriveDurationService.measureForUser` distinguishes **two kinds of nothing**, and the two routes treat the second kind DIFFERENTLY, on purpose — see `UserDriveTimeWriter`'s class javadoc for the full outcome table across {rows stored, no answer, confirmed unreachable, home moved} × {manual, scheduled}. **No answer from ORS at all** (unconfigured, rate-limited, an empty/failed response) leaves rows and stamp exactly as they were, on both routes — a stamp must never advance on nothing learned. **Confirmed unreachable** (ORS answered; no valid duration to any location) is different on the manual route only: `UserDriveTimeWriter.clearIfHomeUnchanged` — a new guarded operation using the same compare-and-set shape `storeIfHomeUnchanged` does, on its own dedicated repository method (`AppUserRepository.clearDriveTimesCalculatedAtIfHomeIs`, a literal `SET ... = NULL` rather than `stampDriveTimesIfHomeIs` called with a `null` instant, so the write never depends on how a bound null binds on a given JDBC driver) and `clearForUser`'s row delete — CLEARS the user's rows and sets the stamp to `null` together, because ORS has just confirmed the stored rows are stale, not merely unmeasured; that is the same state `saveHome` already produces on a home move, which the rest of the product already handles (no "Last calculated" line, the reach lens reads the location as unknown). The **scheduled** job deliberately does NOT do this for the same kind of nothing — it runs with nobody watching, so a transient ORS wobble must not silently wipe a user's drive times overnight; both kinds of nothing are failures there, storing nothing. Both used to be able to leave a genuinely broken state (a non-null stamp with zero rows) behind on the manual path: the no-answer case through a now-deleted `UserDriveTimeWriter.stampIfHomeUnchanged`, and the confirmed-unreachable case because `refreshDriveTimes` used to call `storeIfHomeUnchanged` with an empty list, which clears rows AND stamps in one call — and, in between, a since-corrected fix that merged confirmed-unreachable into the no-answer case entirely, which left a user's now-invalidated drive times in place with no way to know they were stale. The manual refresh's 30-minute cooldown for a *failed or cleared* attempt is tracked separately, in `UserSettingsService.pendingDriveTimeAttempts` (an in-memory `ConcurrentHashMap`, reset by a restart — accepted, since it is a rate limit on a single-instance app, not a record anything downstream reads) — it is the ONLY thing enforcing the cooldown after a confirmed-unreachable clear, since the persisted stamp it leaves behind is `null`. A no-answer response reports the user's own unchanged stamp rather than "now"; a confirmed-unreachable response reports `null`. Migration V157 clears `drive_times_calculated_at` for every user an earlier, pre-fix build left stamped with zero `user_drive_time` rows — a state that cannot recur once every writer follows this rule — and `DriveTimeRefreshJob.needsRefresh`'s own javadoc accepts the one residual cost: a user whose home can never be routed anywhere gets no rows, ever, so their null stamp is re-measured on every scheduled run, matching this job's pre-skip-logic behaviour for exactly that user

## Lite sub-region picks and the change rule (sub-regions-plan S2)

A Lite reader holds up to *n* sub-regions (`SUB_REGION` areas): rows in `app_user_sub_region`, plus two
`app_user` columns, `sub_regions_grace_until` (a UK civil date, inclusive) and `sub_regions_changed_at` (a UTC
wall-clock stamp). Both columns are `updatable = false` and written only by the scoped `@Modifying` updates on
`AppUserRepository` (`startSubRegionGraceIfUnset`, `stampSubRegionsChanged`, `stampSubRegionsChangedIfUnlocked`,
`clearSubRegionsChangedAt`, `clearSubRegionsChangedAtForPickersOf`): the *Column-scoped writes* invariant. *n* is
the single `sub_region_policy` row (default 3, 1..24), read through `SubRegionPolicyService` and edited in the
Operations tab's Sub-regions sub-tab; `photocast.sub-regions.grace-days` (7) and `lock-days` (30) are config.
Pro and Admin never pick: `GET` says `NOT_APPLICABLE`, `PUT` is 403, and picks a demoted-from-Lite Pro still holds
are kept, unused. `photocast.sub-regions.enforce` is only *reported* by S2; nothing is shaped by it until S3.

**The rule** (`UserSubRegionService`, `Clock`-injected, UK civil dates only via `ForecastHorizon.today` /
`civilDate`; `LocalDateTime.now(clock)` for stamps):

- *First choice* (no picks): always allowed; sets `graceUntil = today + grace-days - 1` if it is null; stamps.
- *During grace* (`today <= graceUntil`): any change is allowed and stamps.
- *After grace*: an add-only change under the limit is allowed and stamps nothing; a change that removes a pick
  needs `today >= nextChangeOn = max(graceUntil + 1, changedOn + lock-days)` and stamps.
- An identical set is a 200 no-op. A reader over a lowered limit is flagged `overLimit` and may submit a
  removals-only change without a lock (it stamps nothing); a swap is still locked.
- An admin deleting a sub-region (`AreaService.delete`) clears that area's pickers' `sub_regions_changed_at`
  and deletes the picks, so the re-pick is free.
- Admin tools (`/api/users/{id}/sub-regions`) set picks past the rule (clearing the stamp, leaving the grace end)
  and lift a lock.

**Concurrency.** The lock check and its stamp are one conditional `UPDATE ... WHERE id = :id AND
(sub_regions_changed_at IS NULL OR sub_regions_changed_at < :cutoff)` whose row count is the answer; it runs in
the same transaction as the pick delete and insert, so 0 rows (a lost race) rolls the change back and answers
409 `SUB_REGIONS_LOCKED`. The `:cutoff` is `ForecastHorizon.ukDayStartUtc(today - lock-days + 1)`, so the SQL
agrees with the Java civil-date comparison across a BST midnight. The pick limit is validated before the rule.

**Not in S2.** The registration step (after `HOME`, skipped when `status` is `NOT_APPLICABLE` or `enforced` is
false) and the Settings picker are S4; response shaping by the picks is S3.
