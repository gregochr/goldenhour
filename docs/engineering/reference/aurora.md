# Aurora photography: polling, state machine, banner, viewline

> Moved verbatim from `CLAUDE.md` on 2026-10-22 to keep the always-loaded file small.
> Read the section you need; this file is not loaded automatically.

**Aurora photography**: NOAA SWPC polling (`AuroraPollingJob`, every 5 min, day and night — see the ⚠️ below) via `NoaaSwpcClient` (Kp, forecast, OVATION, solar wind Bz, G-scale alerts; per-endpoint caching) | `AuroraStateCache` FSM (**two** states: IDLE ⇄ ACTIVE — the alert *level* QUIET/MINOR/MODERATE/STRONG is a separate field, not a state) | `WeatherTriageService` (3-point northward transect triage, any-clear-hour pass at < 75% overcast) | `ClaudeAuroraInterpreter` (single `claude-haiku-4-5` call for all viable locations; returns 1–5★ + summary + detail) | `AuroraOrchestrator` (orchestrates full pipeline; Kp + OVATION dual signal) — ⚠️ **every poll evaluates the state machine at most once, and reads tonight through one figure, `maxKpRestOfTonight`** (blocks still ahead in tonight's dark window, the running one included, ended ones never). A daylight poll's level is that figure's; a night poll's is the higher of it and the Kp for now, through one `AlertLevel.fromKp(kp, kp-threshold)`, then raised to MODERATE when OVATION reaches `ovation-probability-threshold` — so the evening keeps a heads-up for a small-hours peak. The alert is attributed to the forecast (planning wording, tonight's window) when the forecast alone reaches the level, and to `REALTIME` only when the conditions now go beyond it. Until 2026-09-14 a night poll could evaluate twice — a lookahead that kept finished blocks (whenever tonight's forecast reached `kp-threshold`), then a real-time path that looked six hours ahead. When the lookahead reached an alert level and the real-time path did not, every poll NOTIFIED, paid for triage and (with a clear location) a Claude call, then CLEARED — up to ~12 an hour; when the real-time path came out higher, the poll that raised the alert paid twice. **Do not split the night poll back into two evaluations, and do not give either poll a horizon of its own** — `deriveAlertLevel()` is the one deliberate exception (below). One NOAA snapshot and one clock reading decide each night poll; "the Kp for now" is NOAA's figure for the most recently *completed* block — its published reading once out, NOAA's estimate for it until then (a reading lands only after its block ends and sits in a 15-minute cache). ⚠️ **A night poll does not end an alert on the estimate for the block just ended while that block's reading is due**: for up to an hour after that block ends (`READING_EXPECTED_WITHIN`), a night poll that would CLEAR holds instead (`AuroraStateCache.wouldClear`; the outcome is `held`, action NONE), so a block NOAA under-estimated is not cleared and then re-bought when its reading lands. The hold has three limits, all deliberate: a reading more than an hour late means a late or stale feed, and the estimate ends the alert; the hold lasts no longer than the night — if dawn comes first, the first daylight poll makes the CLEAR the night deferred (its one evaluation, reading nothing), because after dawn no poll acts on the Kp for now and nothing else would end that alert before the next dusk; and it covers only the block that has ended, so an alert that falls mid-block on the running block's low estimate is still cleared, and bought again if that block is published higher. Do not "fix" that by flooring the Kp for now at the latest reading — it was tried in review and reverted: it let a reading three hours old stand for "now", so after a restart or at a dusk just past a boundary it paid for an alert on a block that had ended hours before, which the next reading cleared minutes later, and it held alerts through a stale readings feed. A daylight poll fetches the full snapshot only when `AuroraStateCache.wouldNotify` says a scoring is coming, and before the state machine moves. `deriveAlertLevel()` is only the (seeded-PAUSED) aurora batch job's rule now and keeps the 6-hour `kp-forecast-lookahead-hours`; the batch it gates writes its results through `AuroraResultHandler` whatever the state machine's state, so un-pausing it needs reconciling. The admin `POST /api/aurora/admin/run` runs the scheduled cycle itself through `AuroraPollingJob.runCycleIfIdle()` — one guard, 409 while a cycle runs; the orchestrator's poll methods are package-private, so nothing outside the aurora package can call them, and inside it only the job does. `AuroraPollingCycleTest` replays whole nights. Still open: no de-escalation hysteresis (`kp-clear-threshold`/`ovation-clear-threshold` are unread); no daylight poll ends an alert on its own reading of tonight (only the admin reset and simulate/clear do, and the first daylight poll's settling of a hold), so an alert standing at dawn for any other reason stands until the next dusk; an alert's first scoring stands until it clears or escalates; and an alert raised by NOAA's figure for the running block is worded as a forecast, though that figure is NOAA's estimate of now | `MetOfficeSpaceWeatherScraper` (Jsoup scraper, 60 min refresh) | Bortle enrichment via lightpollutionmap.info (`LightPollutionClient`, `BortleEnrichmentService`, sb_2025 dataset with SQM conversion) | Map tab aurora mode (selected via `WindowControl`'s night rows; `MapCallout` shows the rating and, since overlay convergence C2, the alert-level word; the Plan-tab overlay's `ForecastTypeSelector` was deleted with the overlay in C5, 2026-10-21, and `MarkerPopupContent`'s aurora section lost its mount, its code kept) | **An aurora-only Map tab** (overlay convergence C3, `utils/auroraTab.js`): `auroraTabOffered` offers the Map tab with no solar forecast at all on a REAL alert — PRO/ADMIN, `active`, MODERATE or STRONG (scores are fetched only from MODERATE), never simulated, its night not ended — and `MapView` adds a live-night aurora row (best = `bestOfNight` over the live `auroraScores`) when no stored result names that night; a tab with no forecast row opens on it in aurora mode. A simulated alert offers neither. The banner's door (C4, `View on map →`, `Map →` below 640px) is `App.handleAuroraViewOnMap`, a `night` door (on the Map tab itself it changes only the window), offered when `hasForecastData || auroraTabOn` and drawn only when the tab has a night row to select (`auroraNightLive` or a rated run); under a simulation it is `Operations →` for an ADMIN (`#manage/metrics`, read by `ManageView` only at mount) and a statement, `Test alert` (`Test` below 640px), for anyone else | `AuroraBanner` (`docs/engineering/aurora-banner-plan.md`, B1–B3, 2026-10-12): severity rides the aurora ramp, chosen from `status.level` (`hexColour` is unread — its amber/red means stand-down everywhere else); at 640px and up a card whose 96×118 slot holds tonight's aurora-field thumbnail (`useAuroraScores`: the live scoring first, the stored run for `resolveAuroraNight(status)` else, restricted to the reader's planning area — `AuroraFieldThumb`, a lazy chunk, `drawGeo` on the aurora ramp) with the best site named beside it, and Kp on a nine-step meter in the same slot until a rated site exists (a 🧪 for a simulated alert, which never asks for scores or a line); the **southern viewline** is drawn on that thumbnail as a dashed amber horizontal line at the projected `southernmostLatitude` (live first, forecast else, `useAuroraViewline`; no flag — the owner enabled it 2026-10-12; asked for only while a real, undismissed, wide-layout alert has a field on screen); below 640px a 56px glow strip; the banner sits inside `WindowFirstBriefingProvider` since B2 | ⚠️ **The Plan's aurora topic names the POLLER's night, not the civil date** (2026-10-08): `AuroraHotTopicStrategy` dates its alert-level topic from `AuroraForecastRunService.currentNight()` (the twin of `AuroraPollingJob.calculateTonightWindow`), so before nautical dawn it is dated YESTERDAY and `PlanWindowProjector`'s `NIGHT` rule puts it on this morning's sunrise — the night the banner's "tonight" is about. Dated from `fromDate` it sat on this evening's sunset, the following night, and the two surfaces disagreed every pre-dawn alert. The Kp-forecast topic covers the night AFTER the poller's (pre-dawn, the coming one), and both details word the night relative to the civil day — *until dawn* / *tonight* / *tomorrow night* — never by which topic emitted them. **Every date test over a topic reads the dates it COVERS** (`HotTopic.coveredDates()`, client twin `windowFirstTopics.topicCoveredDates`: a `NIGHT` topic dated D covers D and D+1), never `date` alone — the aggregator's travel-day filter (over the covered dates still ahead), the Coming up handoff row and Ask's `get_coming_up` timeline all do; a `NIGHT` topic stands on its dusk date in Ask's timeline because `AskReadyFreshness` re-finds an event by the live topic's own date | Aurora viewline (`AuroraViewlineRule`, 2026-10-11, A6): the **forecast** line is a camera-visibility rule, not a table — NOAA's oval edge at `66 − 2·Kp` *geomagnetic* latitude converted to geographic **per longitude** with a centred dipole (IGRF-14 2025 pole 80.9°N 72.6°W, bisection, no dependency) then `HORIZON_ALLOWANCE_DEG` = 4° further south, continuous in Kp (never truncated), clamped 0–9, 17 points at −12..4°E, dipping further south to the west (Kp 6.67 at −2° ≈ 46.5°N; the old table said 54°N for it); `getGlowLatitudeCap` is the same rule at `UK_REFERENCE_LONGITUDE_DEG` (−2°), and so is the FORECAST response's `southernmostLatitude` and summary band (not the curve's west-end minimum, which is mid-Atlantic) so the Map and the Plan card agree for one Kp; the LIVE line's southernmost stays the measured contour's minimum | **`/viewline/forecast` reads NOAA's live forecast on every request** (`AuroraForecastRunService.maxKpRestOfCurrentNight` → `AuroraOrchestrator.maxKpRestOfTonight`, the poller's own figure — do not copy the arithmetic), falling back to `lastTriggerKp`, then to an inactive answer, so the line follows NOAA's revisions with no NOTIFY; the live `/viewline` is the OVATION 5% contour **unclamped** (`applyKpCap` and the Kp table are deleted — they could only move the line north) | **Always live, forecast as fallback, never both** (`useAuroraViewline(enabled)` polls both endpoints every 5 min and returns `{viewline, source}`); live is solid pale `#F2E7D3` at .85 (not green: the aurora field is green), forecast dashed `#ff9900`, labelled `Forecast · Kp 6.7 · 19:40` / `Live · 22:40` from the response's nullable `kp` and `asOf`; every served line logs one INFO `Aurora viewline served: source=…`; `AuroraViewlineOverlay` with the Map legend note gated on the line actually drawing | Alert levels: QUIET/MINOR/MODERATE/STRONG | Admin simulation (`POST /api/aurora/admin/simulate`, `AuroraStateCache.activateSimulation`) is isolated from every user-facing surface: `AuroraStateCache.isSimulated()` gates hot topics and the best-bet advisor's prompt, and a forecast run made against it persists with `aurora_forecast_result.simulated = true` (V154), filtered out of every read `AuroraForecastResultRepository` exposes — see the Aurora API section

**Nights worth a row.** `AuroraForecastRunService.getAvailableDates()` (behind `available-dates`, the Pro/Admin map rows and `/api/aurora/nights`) lists a stored non-simulated night only if its best stored rating is at least `MIN_OFFERED_NIGHT_STARS` (3: the owner's scale, 3 stars is the lowest worth a trip), so a quiet run gives nobody a night row, Pro and Admin included; a live MODERATE/STRONG alert still gives its own night a row. Admins lose map browsing of quiet runs (the run's own response and `forecast/results?date=` still show them).

**The Lite banner** (`docs/engineering/aurora-lite-alert-plan.md`, L2): `AuroraStatusProvider` reads `role` and, for LITE_USER only, polls the role-free `GET /api/aurora/alert` (`getAuroraAlert()`, null on any error) INSTEAD of `/api/aurora/status` (same 5-minute cadence, focus refetch and in-order application; the effect is keyed on the role with a per-run `cancelled` flag). It exposes the answer as the new context value `liteAlert`; `status` stays null for LITE, so every Pro-shaped consumer sees what it always saw, and PRO/ADMIN never call `/alert`. `utils/auroraLiteAlert.isLiteAlertShown(liteAlert, now = appNow())` is the one gate: active, `ALERT_WORTHY` (shared with the Pro banner), night still current, and not `allOvercast` unless STRONG. `AuroraBannerRoot` (App's banner mount) renders `LiteAuroraBanner` when there is no `status` but a `liteAlert`, else `AuroraBanner`; the choice sits above `AuroraBanner`'s hooks so none is conditional. `LiteAuroraBanner`: a card at 640px and up (pill, "Forecast · tonight" / "Active now", "Look north, low on the horizon, after dark.") or a strip below it ("Look north, low"), `SEVERITY` colours, a `ProUpsellDoor` ("Aurora forecast", `testIdPrefix="aurora-banner-upsell"`) where Pro shows its field, best site and viewline, and the same per-level session dismissal. It has no card-level activation and no map door, and makes no scores, locations, forecast-results or viewline request. `role="alert"` is on a text-only wrapper; the door and the ✕ sit outside it. ⚠️ `.wf-aurora-strip` clips its children (`overflow: hidden`), so `.wf-aurora-strip--lite` sets `overflow: visible` and takes the door out of positioning (`position: static`) so the popover anchors to the strip; pinned by `liteAuroraStripCascade.test.jsx`.

**Role-free nights (`GET /api/aurora/nights`, any authenticated role).** `AuroraNightsController` / `AuroraNightsService` serve only the dates a Pro reader would be offered an aurora row for (stored non-simulated nights from `currentNightDate()` on, plus the current night when a real MODERATE/STRONG alert is live; a simulation adds none) and `currentNightEndsAt`; it is the signal behind the Lite Pro door (`docs/engineering/aurora-pro-door-plan.md`), ETag-revalidatable, and opens nothing else under `/api/aurora/*`.

**Role-free alert (`GET /api/aurora/alert`, any authenticated role).** `AuroraAlertController` / `AuroraAlertService` serve the level, active flag, trigger type, a server-side `allOvercast` (dark-sky sites exist and none is clear) and the current night for the Lite banner (`docs/engineering/aurora-lite-alert-plan.md`); a simulation answers QUIET/inactive. "Active and alert-worthy" is defined once, in `AuroraLiveAlert`, shared with `AuroraNightsService`.

⚠️ **`GET /api/aurora/status` no longer calls NOAA on the request thread** (performance P1d). `AuroraController` reads Kp, OVATION and solar wind through `NoaaSwpcClient.getOrRefreshAsyncKp()/Ovation()/SolarWind()`: the cached value is returned at once; past its TTL (15 min, 5 min, 1 min) one single-flight refresh (per feed) starts on a virtual thread, and only a completely cold cache waits for that one fetch. A failed refresh keeps the stale value and the next call retries. `fetchKp/fetchOvation/fetchSolarWind/fetchAll` stay synchronous and unchanged: the state machine's poller decides on them and must never see a stale value. The status body can therefore be up to one refresh behind the poller's.
