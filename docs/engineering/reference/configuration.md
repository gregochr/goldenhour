## Configuration

Never commit `application.yml`. Only `application-example.yml` is committed.

Key config: `anthropic`, `worldtides`, `spring.datasource`, `spring.flyway`, `spring.mail`, `notifications`, `forecast.locations`, `jwt`, `server.port`, `aurora` (enabled, poll-interval-minutes — unread, the interval is the `aurora_polling` scheduler row's, light-pollution-api-key, noaa.*, met-office.*, triggers.*, bortle-threshold.moderate/strong).

`photocast.scheduler.solar-reference.lat|lon` (the point `SOLAR_OFFSET` jobs are timed against; Durham 54.776 / -1.575 by default; both or neither; an invalid value logs ERROR and uses Durham, it never stops startup); `photocast.pipeline.safety-timeout` (ISO-8601, default PT3H30M: the one wait budget per forecast cycle, measured from its first batch submit and shared by WAIT and RETRY_FAILED; only `application-example.yml` sets it, and the production host's hand-edited config must be changed there too if it overrides it); `photocast.pipeline.evening-safety-timeout` (ISO-8601, default PT2H, bounds PT30M..PT3H30M, an out-of-range value fails startup: the evening refresh's own wait budget, measured and enforced like `safety-timeout`, and read by the forecast-cycle watchdog for its evening check).

`photocast.ask.*` (Ask PhotoCast, `AskProperties`; every key is bounded and a bad value fails startup, `application-example.yml` lists each with its range): `enabled` (false), `stub` (false; refused under `prod`), `seed-local-fixture` (false; local H2 only; not an `AskProperties` field — only `AskLocalFixtureSeeder`'s `@ConditionalOnProperty` reads it), `model` (HAIKU; `HAIKU | SONNET` only), `max-turns` (4), `max-tokens` (600), `call-timeout-seconds` (20; may not exceed the deadline), `deadline-seconds` (30), `rate-per-minute` (5), `limit-pro` (30; ADMIN takes it too; Ask is Pro and Admin only, so there is no LITE allowance and a leftover `limit-lite` key is ignored, not a startup failure), `engine-ceiling-multiplier` (3), `daily-spend-cap-usd` (0.50), `ready.max-cycles-per-day` (6), `cache.max-entries` (2000), `cache.ttl-minutes` (30), `log.retention-days` (90). Beside them: the `ask` instances under `resilience4j.retry|circuitbreaker|bulkhead` in every YAML set, and `notifications.admin-alerts.enabled`, which is the spend cap's only signal. The production host's config is hand-edited (the checkout is stale and dirty): read the RUNNING file, never this repo's, before deciding what is on.

`photocast.big-seas.*` (big seas, `BigSeasProperties`, `docs/engineering/big-seas-plan.md` §3 B2; every key is optional, bounded, and a bad value fails startup; the Java field defaults are the only defaults because the host `application.yml` is gitignored): `min-wave-height-m` (3.0, 0.5-15), `max-onshore-angle-deg` (60, 0-180; the circular angle between the wave direction and the way the structure faces), `min-wave-period-s` (8.0, 1-30), `half-window-minutes` (90, 15-180; the half-width sampled around each high water by `MarineWaveRefreshService`, so a change affects only later refreshes) and `max-sample-age-hours` (30, 1-168; `marine_high_water` rows older than this are not served). The first three are read at serve time from the stored numbers, so retuning them needs no refetch. 30 h survives a missed forecast cycle or two (both daily cycles are solar-offset runs that rebuild the briefing, so a healthy system refreshes the rows at least twice a day) but not a stalled job: the nightly and intraday cycles are at most about 14 h apart, so 30 h survives one missed cycle.

---

`coming-up.scoring.*` (`ComingUpScoringProperties`): `bands`, `magnitude` and `rarity` feed the Coming up chronology's surprise score; `recurrent.trailing-window-days` (60) is read by `SlotAtmosphereCleanupJob` to size the slot-atmosphere retention guard. The standing-conditions sub-configs (`recurrent.dust/inversion/mist`, `recurrent.evidentiary-bar-arrivals`, `cadence`, `peak-light-window-minutes`) were deleted with their only reader, `ComingUpConditionsBuilder`, by coming-up-glance B2; a leftover key in a deployed `application.yml` is ignored.

`photocast.sub-regions.*` (`SubRegionProperties`; sub-regions-plan D5/D9): `enforce` (false in the example and local configs; **true in `application-prod.yml` since S6**, pinned by `SubRegionsProdYamlTest`: it is read by `GET /api/user/settings/sub-regions` as `enforced` and by `LitePickShaper`, which with it ON strips the ratings of every location outside a non-Pro reader's picks, marks them `gated`, and serves those bodies `no-store`; with it OFF no response changes and the picks are never read; see `api-endpoints.md`, *Sub-region enforcement*), `grace-days` (7: a reader's first choice starts a free-change period of this many days, the first day included) and `lock-days` (30: after grace, a change that removes a pick is allowed once per this many days). Each day count must be 1..365; a violation fails startup. **The Lite pick limit is not here**: it is the single `sub_region_policy` row (default 3), edited in the Operations tab's Sub-regions sub-tab (`GET|PUT /api/admin/sub-region-policy`).

`photocast.registration.*` (`RegistrationProperties`): `max-users` (10; counts pending sign-ups, excludes admins), `default-role` (`LITE_USER`), `enabled` (true), and the pending-registration hold window `pending-hold-hours` (168), `first-reminder-hours-left` (72), `final-reminder-hours-left` (24). Each hold-window value must be a positive multiple of 24, `final >= 24`, `first - final >= 24`, `first < hold`; a violation fails startup. A production host's `application.yml` wins over these defaults. `spring.mail.properties.mail.smtp.connectiontimeout|timeout|writetimeout` are 10000 ms in `application-prod.yml`, `application-example.yml` and `application-local.yml`: the reminder send is synchronous on a scheduler thread, and Jakarta Mail otherwise waits for ever.

`photocast.dormancy.*` (`DormancyProperties`; audit-followups-plan D): the dormant-account sweep (`DormantAccountSweepJob`, job key `dormant_account_sweep`, daily `0 15 10 * * *`). A LITE_USER (never Pro or Admin; enabled, not pending, with an email) whose `COALESCE(last_active_at, created_at)` is `inactive-days` old is warned by email; if the warning (stamped after that last activity) is `grace-days` old and nothing has happened since, the account is deleted. Keys, all validated at startup (below the floor fails startup): `dry-run` (**true**: the sweep sends nothing, stamps nothing and deletes nothing, and logs would-warn, would-delete and "deletable from" projections), `inactive-days` (90, at least 30), `grace-days` (14, at least 7). The defaults are Java field initialisers, so an absent key is the safe value. The job row is seeded **PAUSED** (V193); "Run now" runs it even while PAUSED, so `dry-run: true` is the lock that matters. Nothing is warned or deleted when no mail sender is configured. To go live: resume the job, read a few dry-run tallies in the logs, then set `dry-run: false` and restart. Logs carry account ids only.
