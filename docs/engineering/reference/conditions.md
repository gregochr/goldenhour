**Wildlife UI**: Hourly comfort rows (temp/feels-like/wind/rain) between sunrise–sunset | Green 🐾 (a comfort-row subject; no map marker — the Map's per-location discs were removed, R2) | No Claude call | ⚠️ **The rows come from `WildlifeComfortRefreshJob` (job key `wildlife_comfort_refresh`, V161), twice a day at 05:30 and 17:30 UTC — restored 2026-10-02 after production had none for seven months.** The old trigger (`RunType.WEATHER`'s `@Scheduled`) was commented out by accident on 2026-02-27, in a commit about per-run-type model config, and never replaced, so every hide read "No hourly forecast available" from then on. The job is deliberately **not** that engine re-triggered: it makes ONE batched Open-Meteo forecast request for every hide (`OpenMeteoClient.fetchForecastBriefingBatch`, chunks of 20) and NO air-quality request, with no Claude call, and reads the six comfort series through `OpenMeteoResponseParser.extractComfortHours`, which is tolerant — an hour with no temperature is skipped, a hole in any colour series costs nothing — where `extractAtmosphericData` throws on one missing cloud hour. **Which places: `LocationEntity.isWildlifeOnly()` — WILDLIFE is the only type.** That is narrower than the deleted synchronous engine's `ForecastCommandExecutor.isPureWildlife` (which also admitted WILDLIFE+WOODLAND and WILDLIFE+BLUEBELL) on purpose: it is the rule the frontend uses to choose which popup draws the table, so writer and renderer agree, and a WILDLIFE+WOODLAND place is briefed as a canopy site. Dates are today..today+5 on the UK calendar; each place-date gets one `HOURLY` `forecast_evaluation` row per full UTC hour from `floor(sunrise)` to `floor(sunset)`, carrying only the comfort columns (every cloud, visibility, humidity, aerosol and tide column is null — nothing reads them for HOURLY). ⚠️ **Replace, not append**: each run deletes that place's `HOURLY` rows for the date and inserts the new ones in one transaction (`WildlifeComfortWriter`, `ForecastEvaluationRepository.deleteHourlyByLocationIdAndTargetDate` — `HOURLY` is a literal in the query, so it cannot reach a solar row). **Cloud inversion**: `InversionScoreCalculator` — likelihood scoring (0–10) from three independent surface terms (temp-dew gap 0–5, wind 0–3, low cloud deck 0–2) behind three gates: low cloud outside 15–80%, no measured temperature reversal aloft, or a stable layer deeper than the viewpoint each cap the score below the band it would otherwise reach | Vertical profile via `temperature_925hPa`/`temperature_850hPa` — **STRONG requires a measured reversal**, and no profile caps at MODERATE (never zero: `ForecastDataAugmentor` logs a WARN so the feature can't die silently) | Location elevation + overlooks_water metadata (V65) | `inversion_score` + `inversion_potential` columns on forecast_evaluation (V66) — Claude's echo, feeding the map popup's badge | Prompt states the measured reversal alongside the score, and tells Claude to weigh it over the score when they disagree | ⚠️ **Two live readers of the score, on two different tables, reconciled by one helper (Phase 2, V158, owner decision 2026-09-30; unified round 3).** `slot_atmosphere.inversion_score` carries the calculator's own score for every inversion-eligible candidate, written inside `fetchWeatherAndTriage` before either triage check — whatever the triage verdict or Gate 4 decision that follows — and `InversionHotTopicStrategy` and Coming up's "Valley inversions" condition (forward peak and trailing history alike) read it via `SlotSignals.effectiveInversionScore()`, which falls back to Claude's `forecast_score` echo whenever the calculator has not scored a slot yet (e.g. a forward slot a `SKIPPED_CACHED` gate held back for up to 36h). The map popup's badge stays on the `forecast_evaluation`/`forecast_score` Claude echo above alone, which only exists for a completed evaluation. The two can disagree — deliberate, see the "record conditions for every place" bullet below.

**Valley mist** (`docs/engineering/valley-mist-plan.md`; **M1a, M1b, M2 and M3 built 2026-10-21**; the plan is complete except the rarity census, which waits on a year of `MIST_CALC`, and the saturation report): mist seen from *beside* it — the riverside, valley floor or lake shore at dawn — the one shape of the phenomenon with no model before (the inversion is mist from above, the woodland lane mist from inside). ⚠️ **It scores the radiative SET-UP, not the model's saturation**: M0 showed Open-Meteo's `best_match` over the UK is already the Met Office 2 km model and even that does not saturate a river corridor (the Brathay on 17 Oct 2026: gap 2–3 °C, RH 81–87%, 37 km visibility all night, mist in the photograph). `locations.mist_prone` (V185, a manual admin fact; a plain column like `overlooksWater`, settable at add time AND on an existing location through `UpdateLocationRequest.mistProne` and the inline-edit checkbox, "Mist forms here: valley floor, riverside, lake shore") is the gate: `ForecastDataAugmentor.augmentWithValleyMist(data, mistProne)` runs in `fetchWeatherAndTriage` beside `augmentWithInversionScore`, before the readings write and both triage checks, for a flagged site only. `ValleyMistCalculator` (pure, 0–10, `MistPotential` NONE < 4 ≤ POSSIBLE < 6 ≤ LIKELY, plus FOGBOUND) sums a clear-night term (mean observer TOTAL cloud over the night-side `MistTrend` slots: T−3h..event for a sunrise, event..T+2h for a sunset), a calm term (night-side minimum wind), a moisture term (night-side MINIMUM temp–dew gap through the shared `MoistureScoring` scale, which `InversionScoreCalculator` also calls — moisture is counted once, and RH is never a second term; `InversionScoreCalculator`'s old private scale moved there unchanged), a cooling term (gap narrowing while the air is not warming), a wet-ground term (`precedingPrecipitationMm`) and a confirmation term (event visibility under 10 km at half weight, full weight under 5 km); cooling scores only when the minimum gap is within 5 C (a dry night cooling toward nothing must not read POSSIBLE); fewer than 2 night-side slots is not scored (null); ⚠️ **the gap is a term, never a gate**, but mean cloud ≥ 70% or a night-side minimum wind > 4 m/s caps the score at 3.9 (NONE whatever the gap). FOGBOUND is event visibility < 300 m with no later slot back above it, decided from the white frame itself, not the score; it has its own constant, NOT `WoodlandVerdictEvaluator.MIST_TOO_THICK_M` (100 m). The bands are priors anchored on the M0 morning fixtures (Brathay, Ingleton, Buttermere LIKELY; windy and overcast NONE) in `ValleyMistCalculatorTest`, cheap to be wrong about until M3. ⚠️ **`MistTrend.MistSlot` carries observer total cloud and 10 m wind (nullable) and `cloud_cover` joined `OpenMeteoClient.FORECAST_PARAMS`** (the layer series cannot stand in for the total); **Astro conditions**: `AstroConditionsService` — nightly observing quality scores for dark-sky locations | Template-scored (cloud cover, visibility, moonlight modifiers) | `AstroConditionsController` with `/api/astro/conditions` and `/api/astro/conditions/available-dates` endpoints | `astro_conditions` table (V64) | ⚠️ **A scheduled job now keeps it fresh (2026-10-11, `docs/engineering/ask-night-plan.md` §2.0 N0); until then `astro_conditions` was written only by the hand-started synchronous engine** (`ForecastCommandExecutor`'s piggyback after a colour run; the engine was deleted in 2026-10), which the scheduled pipeline never reaches, so production held no row after 2026-07-31. `AstroConditionsRefreshJob` (`astro_conditions_refresh`, V170, `0 30 15 * * *` UTC — after the 14:00 intraday cycle, before dusk) scores **tonight and tomorrow night** for every enabled Bortle-enriched location through `evaluateAndPersist`: Open-Meteo only, **no Claude cost**. The nights are `max(AuroraForecastRunService.currentNightDate(), UK civil today)` and that + 1. ⚠️ **Before nautical dawn that deliberately skips the running night**: `OpenMeteoClient.fetchForecastBatch` sends no `past_days`, so its hourly array starts at 00:00 UTC today, and `AstroConditionsService.coversWholeNight` checks only that the array's last hour reaches the dawn *date*, never that it starts at dusk — a pre-dawn "Run now" scoring the running night would use its post-midnight hours alone and overwrite the complete row the 15:30 run wrote. The 15:30 run is in daylight, where both terms agree. ⚠️ **Rows are upserted per (location, date), never deleted**: the service loads existing ids and saves only the locations it rescored, so a location disabled or stripped of its Bortle class after a run keeps its old row — readers must exclude such rows themselves: Ask's snapshot does (`AstroConditionsRepository.findByForecastDateFetchingLocation` — enabled, Bortle-enriched, regioned, and only the night's latest `run_timestamp` generation, see *Ask — the night tool*), while the Map's `GET /api/astro/conditions` still reads them unfiltered; the job deletes nothing. ⚠️ **A run that scored at least one location-date dispatches a NIGHT-ONLY Ask Ready precompute afterwards** (N2; see *Ask PhotoCast*): the Ready `NIGHT_SKY` answer is versioned on this run's `run_timestamp`, so each run withholds the answer written before it, and the pipeline dispatches the precompute only after its own cycles. It runs the `NIGHT_SKY` question alone, on a background executor after the job's `job_run` is complete, so nothing it does (a refusal, an exception, its 5-minute deadline) can fail the run or hold the job's one-at-a-time guard; a zero-scored or thrown run dispatches nothing. Its `job_run` is `RunType.WEATHER` with a null model (no new enum value, so no `LocalH2EnumWidener` line). A failed Open-Meteo fetch is swallowed inside the service (WARN, returns 0, nothing written), so the job cannot tell "no locations" from "fetch failed" and completes the run as 0 scored with a WARN; only a thrown exception (a database failure) fails the run, with the message in `job_run.notes`. Local dev has no `scheduler_job_config` row for it (no migrations run locally), so it is exercised by "Run now" only on a Postgres-backed profile
