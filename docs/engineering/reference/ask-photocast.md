**Ask PhotoCast** (`docs/engineering/ask-photocast-plan.md`, B1–B5, F1a–F5, Z; **off by default** — `photocast.ask.enabled` false answers 404 on every Ask endpoint and the client hides every surface; rollback is the flag, there is no data to unwind): a plain-English question box over the forecasts the Plan tab already serves. **Ask is PRO_USER and ADMIN only** (owner decision 2026-10-24, `ask-pro-gating-plan.md`): a LITE caller is 403 `NOT_ENTITLED` on `POST /api/ask` and `GET /api/ask/ready`, flag on or off, refused by `SecurityConfig`'s `/api/ask/**` matcher ahead of `AskBodyLimitFilter`, `AskFlagInterceptor` and `AskAdmissionInterceptor`; `GET /api/user/settings/ask` stays open to every role. An answer is one or two sentences plus 2–3 **picks** (a location at a window) and/or **event cards** (hot topics), or an explicit *Not in the forecast*. ⚠️ **Two questions, two doors**: a **Ready** answer is precomputed per scope (one per enabled region, plus `ALL`), user-less and free — tapping one makes no request and spends no allowance — while a **typed** question costs an allowance and a Claude call unless a guard answers it first (below). **The Ready catalogue is horizon-aware, not a fixed six** (`ReadyQuestion`, each constant deciding its own availability and text: `BEST_WEEKEND`, `BEST_SOON` — offered only when the weekend question is not — `BEST_NEXT`, `COASTAL_HIGH`, `AM_OR_PM`, `NIGHT_SKY` — "Anything for the night sky tonight?", offered only when tonight's ASTRO night holds at least one pick-eligible (≥ 4★) spot IN THE SCOPE being precomputed, never merely because astro rows exist (see *Ask — the night tool*), `RARE_EVENTS`, `SNOW_TOPS`), because Gate 4 never scores T+4+ and the Plan tab renders six events: on a Monday "best spot this weekend?" is unanswerable, and the bundle's own mock offered it. ⚠️ **A Ready answer is shared by every user, so it can never mention home, drive or reach** — no drive time is in the prompt, the tools or the text; a card's drive is joined on the client from the reader's HOME reach map (`reachById`, labelled ⌂ — never `effectiveReachById`, which the Plan origin replaces with the region-base matrix, or one card would carry two journeys). "Somewhere within an hour of home?" is a typed question. `AskReadyPrecompute.precompute` (serving is `AskReadyServing`) is dispatched on the background executor AFTER `finishRun` in `PipelineOrchestrator.waitAndBriefPhase`, with its own 5-minute deadline: a RUNNING pipeline run forces every later tail settle to `RESETS_ONLY` (see Job metrics), so it must never hold one open, and nothing it throws can reach the run. ⚠️ **A second dispatcher: `AstroConditionsRefreshJob`** (15:30 UTC, N2) dispatches the same precompute after a SUCCESSFUL run (at least one location-date scored; a zero-scored or thrown run wrote no new generation and dispatches nothing), by the same shape — background executor, the precompute's own 5-minute deadline, nothing it throws or any refusal reaching the job, which has already completed its `job_run`. It exists because `NIGHT_SKY` is versioned on the night's astro generation, which that run changes, and the pipeline dispatches only after ITS cycles (14:00, 18:00): without it the 14:00 answer would be withheld from 15:30 until the 18:00 cycle rewrote it. A SCHEDULED astro run takes `precompute(null, NIGHT_ONLY)` and counts against `ready.max-cycles-per-day` like a pipeline one; an admin's "Run now" (the job's `manual` flag is recorded, unlike the pipeline's) takes `precomputeOnDemand(NIGHT_ONLY)`, the route the admin endpoint takes, and is exempt. ⚠️ **It is NIGHT-ONLY**: `AskReadyPrecompute` takes an optional `Set<ReadyQuestion>` (the unfiltered `precompute(Long)`/`precomputeOnDemand()` pass every question, unchanged) and the job passes `{NIGHT_SKY}`, so only that question is asked and written, no other question's stored row is read or rewritten, and the cost after an astro run is at most regions + 1 Haiku conversations (a scope with no ≥ 4★ spot is skipped, not asked); it is still one `ASK_READY` job run, one precompute at a time, refused while another runs and counted against the ceiling when scheduled. It is skipped for a null or `stale()` briefing, the flag off, or a simulation, runs at most `ready.max-cycles-per-day` scheduled times per UK day (with the evening refresh resumed there are four scheduled pipeline precomputes a day, nightly, intraday and evening, plus the astro job's night-only one, against the ceiling of 6; the evening dispatches its own after its run like the others; a count of non-manual `ASK_READY` `job_run` rows — durable across a restart; an admin's on-demand `POST /api/admin/ask/ready/precompute` is exempt and a manual briefing rebuild does NOT trigger it), one precompute at a time, scopes sequential, one question's failure not stopping the rest, an idempotent upsert into `ask_ready_answer` (V165). **Serve-time freshness is all-or-nothing against LIVE data** (`AskReadyFreshness`, shared with the typed cache): a question is withheld whole if any pick's window has passed, any pick's live rating or verdict differs from the one stored, a slot is no longer pick-eligible, an event's topic is gone, the live BEST BET window is not the one pick 1 is on, the question would no longer be offered under the same text, or (`NIGHT_SKY` only) its night's astro generation moved or the night has passed — no partial answers under stale prose; names, dates, labels and safety notes are re-joined from the live snapshot and only the model's `why` survives. Relevance is server-side at both store and serve (`admitsEvent`/`admitsPick`: a `SNOW_TOPS` answer cannot carry an aurora card, a `BEST_WEEKEND` pick must be on a Saturday or Sunday window); an answer that would lose an event carrying a `safetyNote` is not stored at all. `GET /api/ask/ready` is the one Ask route in `HttpCachingConfig`'s ETag allow-list (user-independent, Bearer, no role gate).

**Ask — the window spread** (`docs/engineering/ask-window-context-plan.md`, W1, W2 and W3 built 2026-10-20): `list_windows` serves each solar window's rating distribution over the question's scope (`AskSnapshot.Spread`, a pure fold over served slots: the five band counts, `gameOn` = 4★+, pockets (regions holding a game-on place, at most four), region tallies by served kind) — a wood and a neighbour-guard-held place are out of the counts, a thin region (`!verdictEligible`) is counted as a region and not in the bands, and a slotless region is "stood down" only when `BriefingRegion.coverageReason` (set by `BriefingHonestyFilter.fullRewrite`, serve path only, carried by all nine withers) is `STOOD_DOWN`, never for the `UNKNOWN` the filter words the same way. The prompt carries the owner's scale and a hint, not a script; nothing in the validator reads a threshold. The honest "nothing worth going out for" Ready answer is admitted by ONE predicate, `ReadyRelevance.mayHaveNoPick` (`AskSnapshot.hasGameOn` over the offer's `coveredWindowIds` with the question's own `admitsSlot`), read by the validator's anchor rule, `ReadyRelevance.violation` and `AskReadyFreshness.check`; `anchoredWindow` is unchanged. An `AskAnswer` carries `windows` (the whole `Spread` of every window `list_windows` returned, each pick's solar window and a Ready question's covered windows, built by the validator) and `AskReadyFreshness.recheck` withholds the answer whole when any differs by record equality or a carried window has left the set; a stored Ready row also keeps `coveredWindowIds` (a property of `answer_json`, no column) which must equal the live offer's. `AskAnswer` ignores unknown properties, so any later field is read fail-soft. **The client line removed (2026-10-27):** the per-window line under the summary was removed from the answer card at the owner's request (it repeated the summary and pushed the picks down); `windows` is still served and still drives `AskReadyFreshness`, and the client no longer keeps it. `AskAnswerParser` decodes HTML character references (`&amp;`, `&lt;`, `&gt;`, `&quot;`, `&#39;`, `&apos;`, numeric `&#NN;` / `&#xHH;`) in a single pass in the model's free text only (`summary`, `missing`, each pick's and event's `why`), never in `windowId`, `type` or dates, because the model sometimes wrote "Northumberland &amp; Tyneside" and React prints text verbatim. Decisions Q1–Q7 are recorded in the plan's §6 (3★ words only; `BEST_*` kept offered and anchored; the framing reading of "must not lead with a 4★ pick").

**Ask — the engine.** `ClaudeAskEngine` is a tool loop: at most 4 model turns, `tool_choice` `any` (every turn must be a tool call; a text-only turn is unreachable except via `max_tokens` or a refusal, and stays a FAILED outcome behind that) except the last permitted turn, which forces `submit_answer` (`tool_choice` `tool`, plus `ClaudeAskEngine.LAST_TURN_LINE` appended to that turn's tool-result message) so a model that explores for every turn still answers, `max_tokens` 600, six tools for a Ready conversation (`list_windows`, `rank_spots`, `rank_night_spots`, `get_hot_topics`, `get_coming_up`, `submit_answer`) and seven for a typed question (`look_up_place` after `rank_spots`, *Ask — look_up_place*) answered in-process over one `AskSnapshot` built from `BriefingService.getCachedBriefingForApi()` — the Plan tab's own assembly, so retraction, the sample gate and the honesty filter are inherited, and no store in *Where a rating lives* is read directly — memoised 30 s (a rewound admin request neither reads nor writes the memo). **The reply is the `submit_answer` tool call's input, not prose.** The Claude and stub engines share one conversation frame, `AskConversation` (a collaborator, not a base class: it opens the conversation — options checked first, a blank question a FAILED run before any tool exists — and closes it through `submit`/`rejectSubmission`/`fail`, so every FAILED run reports `personal` as the tools saw it), and one event-type identity, `AskEventType.key` (strip, upper-case, `-` read as `_`, so the almanac's `lunar-eclipse` is the hot topic's `LUNAR_ECLIPSE` at every site that compares a type; the type a card carries on the wire stays as served). The `get_coming_up` timeline and its 90-day horizon are `AskSnapshot.timeline`/`AskSnapshot.MAX_COMING_UP_DAYS` — the one definition the tool, the validator's offered-events count and the freshness check share. A FAILED typed run's reason is logged once at INFO by `AskService.runEngine` (`[ASK]`, user, turns, reason through `LogSanitizer`); `AskAnswerValidator` is pure and logs nothing. ⚠️ **The validator decides everything** (`AskAnswerValidator`; nothing safety- or cost-relevant depends on the model behaving): a pick survives only if `(locationId, windowId)` was returned by `rank_spots` or `rank_night_spots` IN THAT CONVERSATION **or offered by the thread** (an earlier answer's pick, `AskEvidence.ThreadFact`) and is still pick-eligible live and in scope, at most 3 at distinct locations (4 for a ranking follow-up, *Ask — the thread*), ranks renumbered; an event only if its type came from a tool or the thread (still flagged live); summaries and `why` are word-capped (60/24), brand-sanitised and URL-stripped; every card fact (name, region, rating, verdict, time, tide) is joined from served data, never the model's; a malformed `submit_answer`, a refusal, `max_tokens`, a turn with no tool call, a last turn without `submit_answer` (reachable only if the forced call is malformed or cut short), or a missed 30 s deadline is a FAILED outcome. ⚠️ **Pick-eligible is the Plan tab's own rules and nothing looser** (`AskSnapshot.isPickEligible` for a solar pick; a night pick's sibling rule, `isNightPickEligible`, is in *Ask — the night tool*): non-canopy (a wood's star means the opposite of a sky star), a rating on Claude's 1–5 scale and ≥ 3, a `pickEligible()` region (a sufficient sample; the force-evaluation exemption sets a verdict but not a pick, 2026-10-22) — the 2026-09-29 shape, a handful of hand-run 4★ ratings in a 253-location catalogue, must never crown a region, and no rating exempts an ineligible one — and not a neighbour outlier (`BriefingSlot.neighbourOutlier`, the neighbour guard below: a rating far above every nearby place keeps its star but is never offered as a pick) — and a window in the **window set**. ⚠️ **The window set is the served `renderedEvents`, NOT "events with a non-null `window()`"**: every event summary carries a window, only the first six upcoming events are rendered (`PlanRenderLimits.MAX_VISIBLE_EVENTS`); plus not passed (`PlanWindowProjector.hasPassed`, the shared test) and not a travel day (the served briefing marks none, so `TravelDayService.isTravelDay`); solar windows only (the night windows are the night bullet's own set). A generic "best" answer must lead with the BEST BET window — the prompt says so, and a Ready `BEST_*` answer that does not is *discarded*, never stored — because two bests on one screen is the aggregator divergence `plan-panel-data-contracts.md` records. Tide travels as two fields and is never merged: `tideState` (the served band) and `tideAligned` (the location's own wanted water); the prompt says tide "suits" a spot only when `tideAligned` is true — the map's one tide gate, again. ⚠️ **The solar-eclipse `safetyNote` must reach every surface, Ask included**: the model has no field for it, an event re-joins it from the served topic, and the almanac's `eclipse` entry (never `lunar-eclipse`, whose note is not a safety warning) has none of its own, so the snapshot attaches `EclipseHotTopicStrategy.SAFETY_NOTE` — one string, one home; the client draws it outside every role gate and narrow-viewport drop (`askCss.test.js` pins that). The Coming up tab itself still shows no solar-eclipse warning — an open owner question. ⚠️ **`generatedAt` is a label and an invalidation hint, not the identity of the ratings**: ratings are re-enriched and hot topics recomputed on every serve, so freshness is always checked against live data, never inferred from it. The model is `photocast.ask.model`, `HAIKU | SONNET` only (no `model_selection` row, nothing in `CONFIGURABLE_RUN_TYPES`; Sonnet 5.5 cannot disable thinking, which breaks the token and time budgets). Resilience is its own door (see *Resilience*: the `ask` retry, breaker and bulkhead; SDK retries off; a 20 s per-call timeout; the 30 s deadline enforced by the ENGINE, which stops waiting and interrupts a call). **Cost**: `RunType.ASK` is one `job_run` per UK day, found or created BEFORE the first model turn under an in-JVM lock (a database that cannot record the money stops the call that would have spent it), with a column-scoped `total_cost_micro_dollars` increment after each turn because `completeRun` sums once; `ASK_READY` is one run per precompute; every turn, failed ones included, is an `api_call_log` row (no bodies — the request is the reader's question). ⚠️ **The accounting latch fails closed**: a turn whose log insert fails after Anthropic answered is kept in a bounded in-memory holder and latches (`AskJobRunService.accountingAvailable()`, which asks `UnrecordedTurnHolder`); the typed-spend figure adds the unrecorded cost and bypasses its 30 s memo; a `CallGate` inside `createAskMessage` — after the bulkhead permit, before every attempt, a retry's second included — refuses the attempt, the run returns FAILED with `AskRun.ACCOUNTING_UNAVAILABLE`, `typedAvailable` reads false and the POST answers 503 `TYPED_UNAVAILABLE`. What cannot be closed is stated: the calls already in flight when it latches (at most the bulkhead's four) and a restart losing the holder. `StubAskEngine` (`photocast.ask.stub`) answers from the same tools with templated text, no client call and no job-run dependency; **exactly one `AskEngine` bean exists for any value of the flag** (`AskEngineSelection`, two `@Conditional`s that are each other's negation — two `@ConditionalOnProperty` would leave none for `stub=yes`), and ⚠️ **`stub=true` under the `prod` profile fails startup** — neither a template for readers nor a silent fall-back to the engine that bills the key.

**Ask — the Ready `rank_spots` bound.** For a Ready question that picks places (`ReadyBasis` present, `question().picks()`, not `nightBound()`), `AskConversation.open` hands `AskTools` the offer's `windowIds()` (the set `ReadyRelevance.admitsPick` admits picks from) and `rank_spots` is confined to it: no `windowIds` ranks only those windows; named `windowIds` keep the unknown-id error, are then silently intersected with the bound, and fail (naming the allowed ids) only when the intersection is empty, because the prompt names `coveredWindowIds()`, a superset of `windowIds()`. Typed conversations and the night and events questions are unbounded. Without it a Sunday `BEST_WEEKEND` led with a Monday pick and was discarded (`docs/engineering/ask-ready-rank-spots-bound-plan.md`).

**Ask — `look_up_place`** (`docs/engineering/ask-place-lookup-plan.md`; owner decisions D1–D3, 2026-10-22; the defect: "Why is Alnmouth a 4 on Saturday morning?" was answered "Not in the forecast" because `rank_spots` returns only pick-eligible slots and the Map's thin-sample 4★ places are not). A question about ONE named place is an **explanation, not a pick**: `AskTools.lookUpPlace(name, windowIds)` returns the place's served rating, verdict, headline and tide fit per window whether or not PhotoCast would recommend it, with a `status` (decided in this order by `AskTools.classify`: `UNRATED`, `CANOPY`, `BELOW_GAME_ON`, `NEIGHBOUR_OUTLIER`, `THIN_SAMPLE`, `PICK`; the rating floor precedes the guard and region tests so a 2-star place is never blamed on a thin sample) and our fixed reason, said once per status in a top-level `reasons` map rather than on every row, so the model can say why it is not suggesting it. ⚠️ **The result is row-capped** (`MAX_PLACE_ROWS` 6, places `MAX_PLACE_MATCHES` 4; the exact match's rows first, a cut named in `note`): the 9,000-character `RESULT_CHAR_CAP` is per conversation and `list_windows` comes first, so one lookup is held to 4,500 (measured worst case 3,785) and the prompt tells the model to pass the `windowIds` the question is about. ⚠️ **It reverses part of neighbour-guard G2 for this one route (D2)**: a held-back neighbour outlier IS named with its star when the reader names it, and the answer must say it is rated well above the places beside it; `rank_spots`' held-back note (a count, never a name) is unchanged. ⚠️ **It adds NOTHING to `AskEvidence.pairs`**, so the validator drops any pick the model makes from a lookup (`evidence.offers` fails, and `resolvePick` refuses a non-eligible slot anyway); a place to recommend must come from `rank_spots`. `classify` ends in a check against `AskSnapshot.isPickEligible` and throws if they disagree, so a new pick rule missed here fails a test. Matching is whole words as a contiguous run, lower case, apostrophes removed, not `AskQuestionSanitiser`'s normaliser (its filler list would drop a place's own "the"); exact names first, at most `MAX_PLACE_MATCHES` (4) places, each carrying every window it is in; a name found only outside the question's regions returns no places and a scope note, never a rating. Solar only (no aurora gate to cross). ⚠️ **Closest spelling (`ask-place-explain-plan.md`, E2)**: when the exact pass and the area pass find nothing, `lookUpPlace` runs a fallback, but only if no place, alias or area in ANY window of the snapshot carries the words (X9; such a hit returns today's note, so a correct spelling is never "corrected" into another place). It scores every distinct spelling in the snapshot (place names, aliases, area names and aliases, in scope or not) with `PlaceNames.prefixDistance` (X8: leading runs of the name only, spaces removed on both sides, the first letter must match, optimal-string-alignment distance), within `PlaceNames.allowedEdits` (0 for up to 3 letters, 1 for 4 to 5, 2 for 6 to 8, 3 from 9). One spelling text clearly closest (alone at the least distance d, and with none within d+1 when d is 2 or more) is looked up again ONCE with its words (X7: so a name shared by several places finds them all, an area name reaches the area branch, and `matchedAlias`, the row caps and the scope note behave as normal) and the result carries `closestTo`, the reader's spelling; the prompt makes the answer open "Assuming you mean <name>," (X10). A tie returns no places and up to `MAX_SPELLING_SUGGESTIONS` 3 in-scope place names as `suggestions` with a note, and the model calls again (X12: list_windows, look_up_place, look_up_place and submit_answer use all 4 turns, so that question cannot also reach `rank_spots`). A winner found only out of scope returns `PLACE_OUT_OF_SCOPE_NOTE` with no `closestTo`, so no name leaks; a winner found only outside the requested windows returns `closestTo` with no places. Nothing is added to evidence, so a guessed place is never a pick. ⚠️ **The forecast's own reason (`ask-place-explain-plan.md`, E1)**: `AskSnapshot.Slot` carries the served `summary`, `skyRating`, `fierySky` and `goldenHour` (from `claudeSummary`, `skyRating`, `fierySkyPotential`, `goldenHourPotential`, all cleared on retraction), and `PlaceInfo.detail` (`PlaceDetail`, null-omitted) returns them **only on the rows of the one place the answer is about** (X5: the first ordered place when it is exact, or when it is the only place matched; at most `MAX_DETAIL_ROWS` 4, in window order). X6: no detail for `UNRATED`, `NEIGHBOUR_OUTLIER`, a row with no summary, or the `ForecastResultHandler.SKY_NOT_FORECAST_SUMMARY` placeholder (it names "Claude"); a `CANOPY` row gets the summary only (its light and potentials read the opposite way). The summary has `"` swapped for `'` and `\` dropped (so JSON escaping cannot grow it) and is capped at `SUMMARY_CAP` 200. **When any row carries detail the row cap is `MAX_PLACE_ROWS_WITH_DETAIL` 4, not 6** (a detail row is about 300 characters; the "Showing N of M" note uses the cap that applied); measured worst cases with detail: 3,666 (6 windows) and 3,942 (a 40-character alias), under the same 4,500 bound. X2: **no raw weather numbers** (cloud %, visibility and humidity are the triage point forecast, not the directional sample the rating used). X3: the summary describes the sky while the star is `RatingCombiner`'s sky-and-tide figure, so when `skyRating` is above `rating` the answer says the tide pulled it down, using `tideFitPhrase`. X4: Fiery Sky and Golden Hour are named as the Pro UI names them, may be quoted out of 100, are mentioned only when the question asks about the light's character, and are **never ranked against each other** (they are calibrated differently, so "more fiery than golden" would be an unlicensed derivation). `rank_spots` output is unchanged byte for byte, and the Ready prompt and tools carry none of it. ⚠️ **Typed questions only**: `AskToolSchemas.tools(withUser, withThread, withPlaceLookup)` is given `!ready` by `ClaudeAskEngine`, and `AskPromptBuilder.systemPrompt` rewords the investigation sentence and adds the `look_up_place` bullet only when `hasUser` (a typed prompt; `RULES` itself is unchanged), so the Ready precompute's tool list and prompt bytes are exactly as before. ⚠️ **Cache consequence**: the typed cache stores only an answer carrying a pick or an event, so an explanation answer (answerable, no pick, no event) is never cached and each such question costs an engine call; accepted. The client needs no change: an `answerable: true` answer with empty `picks`/`events` renders as a summary (`normaliseAnswer` sets the `cant` phase only for `answerable === false`). The real-API script is `AskPlaceLookupRegressionTest` (`prompt-regression`, assertions pending the owner's approval, never run).

**Ask — named areas and location aliases** (`docs/engineering/ask-named-areas-plan.md`, A2; the defect: "Does Hadrian's Wall look good this weekend?" was answered "Not in the forecast" because no location is called "Hadrian's Wall"). Admin-owned tables (V189: `area`, `area_alias`, `area_location`, `location_alias`) are read once per snapshot build through the seam `AskAreas` (`RepositoryAskAreas`: maps inside a read-only transaction; ⚠️ any exception is WARN + empty and the snapshot still builds, because Ask must still answer) into `AskSnapshot.areas` and `AskSnapshot.locationAliases` (the last two record components, with delegating constructors so older `new AskSnapshot(` sites compile). Aliases are sorted everywhere by `AskAreas.ALIAS_ORDER` (fewest characters, then case-insensitive alphabetical), never by load order. **D3**: `look_up_place` matches a named area (the query's words CONTAIN the area's name or an alias as a contiguous run, so "Steel Rigg on Hadrian's Wall" matches; "wall" alone matches nothing) and returns an `area` result (`AreaInfo`: per window, at most `MAX_AREA_WINDOWS` 4 windows and `MAX_AREA_PLACES` 6 places each, with `rated` / `fourStarOrBetter` over ALL in-scope members, a wood and an unrated place excluded, and `status` from `classify`). It adds NOTHING to `AskEvidence.pairs`, exactly like a place lookup. **D10**: an exact place match, by name or alias, beats an area; a partial place match gives way to it with an "Also matched places" note. A place found by another name shows its real name plus `matchedAlias` (only when the name itself did not match). **D4/D5**: `rank_spots` gains `areaName` (typed conversations only: `AskToolSchemas.rankSpots` adds it when `withPlaceLookup`, and `AskTools` refuses it when `!user.hasUser()`), resolved through the same area matcher (name or alias); its results are ordinary pick-eligible, evidence-recording `rank_spots` results, and the held-back note counts only the area's members. Ready's tool list, `rank_spots` schema and prompt bytes are unchanged. The typed prompt's `PLACE_FIT_AFTER` now reads "returns no places and no named area" (⚠️ an area result has empty `places`, so the old wording sent it to "not in the forecast": the defect itself); every new sentence says "named area" because "area" already means region scope. `KeywordAskIntentMatcher.placeNames` includes area names, area aliases and location aliases (defence in depth: the Ready word rules already decline today's names). Worst cases measured: a named-area result 4,024 characters, a place found by a 40-character alias 4,199, both pinned under 4,500 in `AskToolsNamedAreaTest`. ⚠️ **Typed-cache note**: an area-filtered `rank_spots` answer carries picks, so the typed cache may store it; its key is scope, date, `generatedAt` and question, so an admin's edit shows from the next briefing build. The real-API script is `AskNamedAreaRegressionTest` (`prompt-regression`, assertions pending the owner's approval, never run). ⚠️ **Where areas are edited (A3)**: admin only, in the Operations tab's location management view: an "Areas" section (create, rename, aliases, member picker, delete) over `/api/areas*`, and an "Also known as" field on the location edit form over `PUT /api/locations/{id}/aliases`, saved AFTER the location's own `PUT`. `AreaService.update` loads the row and changes name and aliases only (the membership endpoint is the sole writer of `locationIds`, so a rename keeps the members); every name goes through the one `NameNamespaceGuard`, comparing `util/PlaceNames.words` forms (so "Hadrians Wall" equals "Hadrian's Wall"): an **area name or alias** may not equal another area's name or alias, nor equal or sit inside (as a run of whole words) any location name or location alias; a **location alias** may not equal another location's name or alias, nor an area name or alias, nor contain one as a run; a **location name** (`LocationService.add` and the rename branch of `update`, called with the location's own id) may not equal another location's name in normalised form, nor any location alias other than its own, nor an area name or alias, nor contain an area name or alias as a run (otherwise a place called "Hadrian's Wall" would hide the area, since an exact place beats an area). Shape: names 2 to 80 characters, area aliases at least two words. A missing `locationIds` or `aliases` list is 400 (only `[]` clears). Clashes (and a unique-index race) are 409 `NameClashException`, except a location add or rename, which keeps its 400 `IllegalArgumentException`.

**Ask — sub-regions are areas** (`docs/engineering/sub-regions-plan.md`, S1). A **sub-region** is an `area` row with `kind = 'SUB_REGION'` (V191; `AreaKind`, null read as `NAMED`) and a `region_id`: 24 of them partition the four enabled regions, so Ask's area machinery knows their names and aliases with no new code path. ⚠️ **Membership is NOT in `area_location`**: a sub-region's members are the `location_sub_region` rows (primary key `location_id` = one sub-region per location), written ONLY by `SubRegionMembershipService` (move = update-then-insert, because local H2 has no `ON CONFLICT`; a location's region must equal the sub-region's, a region change on a location deletes a now-mismatched membership and logs it) and read by `RepositoryAskAreas.load()`, which swaps them in for a sub-region's `locationIds`. `AreaService.setLocations` refuses a sub-region (400, "set a location's sub-region on the location itself"); creating one needs a `regionId` (400 without), deleting one with members is 409 `AreaConflictException`, and an area's kind and region never change on update. "Hadrian's Wall & Tynedale" is the one deliberate containment of another area's name (the V189 "Hadrian's Wall" stays a `NAMED` area): `matchArea` takes the longest matched run, so "Hadrian's Wall" resolves to the Wall area and "Hadrian's Wall & Tynedale", "Tynedale", "South Tyne" to the sub-region. **One area per call**: `look_up_place` answers the single best area match (`AskTools.matchingAreas` orders by matched run length, then name) and adds an **"Also matched areas: …; this result is for X only, so call look_up_place once per area."** note (at most `MAX_ALSO_AREAS` 5, never an area whose matched words are only part of the best match's words, so the Wall area is not offered beside its own sub-region); `rank_spots` still takes one `areaName`; the typed prompt's `PLACE_FIT_AFTER` carries one sentence telling the model to call once per named area. `KNOWN_AREAS_CAP` is 1,200 characters (was 200) so all 25 names fit in an unknown-`areaName` error. **Ask — "close to home" is `rank_spots.nearHome`, the saved local radius, as the crow flies** (T3, `docs/engineering/ask-thread-plan.md` §2.6). `nearHome: true` keeps spots within the asker's saved `local_radius_miles` of their home point (`photocast.close-to-home.radius-miles`, 22, when none is saved; the UI clamps 10-50) by `GeoUtils.distanceMiles`, the measure the retired Close-to-home panel applied to that radius. The server resolves it: `AskService` builds `AskUserContext.home` from the user row it already holds (no extra query) and the coordinates come from `AskLocationNames` (enabled locations by id: name, lat, lon), memoised once per conversation and shared with the thread's name lookup. ⚠️ **Stated divergence, accepted:** the Map's reach lens and `maxDriveMinutes` measure DRIVE time; `nearHome` measures straight-line MILES, so a LITE account with a home and no drive times gets it (distance needs no ORS), and the answer says **"within N miles of home"** (the tool result carries `withinMilesOfHome`) and never "within reach", which this file forbids without a drive time. No home saved answers `nearHome is not available: no home postcode is saved.` (an empty result with a note, not an error); a Ready conversation refuses the argument as it refuses `maxDriveMinutes`. `personal` is set by EITHER argument, server-side. The prompt rule: 'close to home', 'near', 'nearby', 'local' with no number is `nearHome: true`; a number of minutes is `maxDriveMinutes`; 'closer' in a follow-up is a `maxDriveMinutes` below the earlier picks' drive, or `nearHome` if it was not used (this replaced #1078's "no number means 60 minutes"). The admin dry-run's context carries no home, so `nearHome` there answers "not available". The typed cache keys a personal answer by user id for 30 minutes, so a change of home or radius inside that window can serve the earlier answer once.

**Ask — the thread** (`docs/engineering/ask-thread-plan.md`, T1–T5; owner ask 2026-10-10, after the first real session on v2.25.0: "anything for sunrise with tide alignment this weekend?" → "anything closer to home?" → "neither of those take my fancy, what's the best sunset option?" → "rank those options"): a typed question can be a **follow-up**. `POST /api/ask` takes an optional `thread` — the session's earlier exchanges, oldest first, each `{question, summary, picks: [{locationId, windowId}], events: [{type, date}], generatedAt, ready?, nightVersion?}` (`nightVersion` is the opaque string a night answer carried, echoed verbatim and absent from a solar exchange, so a solar thread is byte for byte what it was) — ids plus the reader's and the model's own words, never a card fact; the server re-joins everything else. ⚠️ **A thread adds a second way a pick can be OFFERED to the model, never a way for a stale one to be SERVED**: the validator still decides everything, and an offered pick must be pick-eligible live and in scope at the moment of the answer. **Validation** (`AskThreadValidation`, all 400 `INVALID`): more than `photocast.ask.thread.max-exchanges` (8, bounds 1..20) exchanges, a null entry, an earlier question outside the live question's sanitiser rules or over 200 RAW code points, a summary that is blank, over 500 RAW code points (counted before any collapse) or holding a control, format, emoji or combining character (`AskQuestionSanitiser.sanitiseThreadSummary`, then the validator's `clean`: URLs, brand names, 60 words), a pick without a positive location id and a well-formed window id, more than four picks or ten events in one exchange, an event type that is not a plain token, a missing `generatedAt`, a `nightVersion` that is not in the server's own format or is over 200 characters. The validator bounds every SERVED summary to the same 500 (`AskAnswerValidator.THREAD_SUMMARY_MAX_CODE_POINTS`, cut at a word boundary after the 60-word cap) and strips what a follow-up would refuse (`AskQuestionSanitiser.refusedInProse`, one shared predicate), so a served summary always round-trips into the next follow-up. ⚠️ **The body-limit invariant** (`AskBodyLimitFilter`): 8 KiB + 10 KiB per permitted exchange (88 KiB at the default cap, 208 at 20), and the per-exchange figure holds BECAUSE the raw-length caps above bound one exchange before any normalisation; it admits, with margin, every body OUR CLIENT sends (compact JSON, ASCII keys unescaped, `threadForWire` having stripped and collapsed), and promises nothing for a body that spends its bytes on `\u`-escaped keys or whitespace. **The thread ends when the forecast moves**: once the snapshot exists, a TYPED exchange whose `generatedAt` is not the live run's drops the WHOLE thread, the question is answered fresh and the response carries `threadReset: true`, `threadResetReason: "forecast updated"` on every path (a Ready-origin exchange is never compared — its `generatedAt` is the precompute's, and its picks re-join live, which is the Ready freshness rule). ⚠️ **A second trigger, the night forecast** (`docs/engineering/ask-night-plan.md` §2.2): ANY exchange, typed or Ready-origin, whose `nightVersion` is not the live one (`AskThread.nightStaleAgainst`) also drops the whole thread, with `threadResetReason: "night forecast updated"` (the briefing's own reason wins when both moved) — a night summary rests on facts (the aurora alert, a clear-sky claim) that move without the briefing moving, and a Ready-origin exchange gets no exemption here because its picks re-join live and a verbatim night summary does not. **Guards**: the pre-filter reads the NEW question only (a "car park" follow-up still refuses); the Ready matcher and the typed cache are SKIPPED for a follow-up (a question leaning on earlier answers is never a catalogue question, and its cache key would need the thread); otherwise it is charged, capped and reserved as any typed question — one allowance unit, one engine call, `engine_calls` never refunded — and logs one INFO line (`[ASK] User N answered a follow-up: outcome=… thread=N reset=…`, ints only, never the thread's text); a fresh question's log, prompt and cost are unchanged. **What the model sees** (`AskThreadContext`, built once at `AskConversation.open`, which hands ONE `AskLocationNames` lookup to the tools and to the thread): each earlier pick is re-joined live from the snapshot in `rank_spots`' vocabulary (a night pick in `rank_night_spots`', resolved with the asker's own `canSeeAurora`, and a night exchange's summary is never rendered to the model) (with its `locationId` and `windowId`, which the model needs to name it again); a pick whose slot has gone reads `<name> · no longer in the forecast` (the name from the lazy enabled-locations map, or `a place no longer listed`), one that is present but no longer rated well enough `no longer rated well enough to pick`, one outside the follow-up's scope (the Map's scope segment can move between questions) `outside the area you are now asking about`, and none of those is offered; an earlier event is offered only while it is still a live, in-scope hot topic or almanac entry (served label and safety note). The thread rules join the SYSTEM prompt only when a thread exists ("earlier picks are real candidates; resolve 'closer', 'those', 'the other one' against them; call `rank_spots` again for new places"), so a fresh prompt is byte for byte unchanged. **Ranking rule** (two pick rules, chosen per answer): a FRESH answer is up to 3 picks at distinct LOCATIONS; a **ranking follow-up** — the thread offered earlier picks and EVERY pick the model submitted is one of them — is up to **4** picks distinct by **(location, window)**, so "rank those options" can return Whitby at sunrise and at sunset (the follow-up's `submit_answer` schema advertises `maxItems` 4); a MIXED answer (any submitted pick that is not a thread pick) falls under the fresh rule, because the relaxation exists to rank the reader's own options whole, not to let a new-places answer repeat a place. **Turning the earlier places down is code, not a prompt rule** — the prompt alone failed on the owner's own script (the two earlier places came back in three of four real runs): `ReadyIntentRules.turnsDownEarlierPlaces`, a conservative whole-word phrase test applied to a follow-up's question in `AskConversation.open` (`neither`, `not those`, `none of those`, `been to both|those|them|all` — never after `not`/`never`/`haven't` — `don't fancy`, `something else`, `somewhere else`, `other than|apart from|instead of those`; a bare "those" or "I've been to Bamburgh" does not match). On a match `ThreadFact.turnedDown` holds the LOCATIONS of every earlier pick in the thread (all exchanges, offered or since gone), the validator drops any submitted pick at one of them at every window (a count is logged at INFO, never a name), the prompt marks each earlier pick "the reader has turned this place down" and says they must not be picked again, and the stub honours it;
