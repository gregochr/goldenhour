# Core pipeline, scoring, evaluation, command pattern, cost, job metrics, resilience, batch cache primer

> Moved verbatim from `CLAUDE.md` on 2026-10-22 to keep the always-loaded file small.
> Read the section you need; this file is not loaded automatically.

**Core pipeline**: Open-Meteo → Claude → H2 | Scheduled evaluations (06:00 + 18:00 UTC, T through T+7) | Notifications (email, Pushover, macOS toast)

**Scoring**: Two scores (Fiery Sky 0–100, Golden Hour 0–100) + 1–5 star rating | Dual-tier: enhanced (directional cloud) for PRO/ADMIN, basic (observer-point) for LITE | 3-point cone cloud sampling at 113 km offset (azimuth ±15°) via `GeoUtils` + `DirectionalCloudData` | Far-field sample at 226 km for horizon strip vs blanket detection | Cloud approach risk detection (`CloudApproachData`, `SolarCloudTrend`, `UpwindCloudSample`) | Cloud inversion scoring (`InversionScoreCalculator`, 0–10 from temp-dew gap/wind/humidity/low cloud) | Solar-aware slot selection (`findBestIndex()`) | Sahara Dust badge (AOD > 0.3 or dust > 50 µg/m³ with PM2.5 < 35) | Rising tide warning badge (high tide within ±90 min of solar event)

**Evaluation**: Single `ClaudeEvaluationStrategy` parameterised by `EvaluationModel` | `PromptBuilder` + `MetricsLoggingDecorator` (GoF Decorator) | `NoOpEvaluationStrategy` for wildlife | `AnthropicApiClient` with Resilience4j `@Retry` + `@CircuitBreaker` (`ClaudeRetryPredicate`) | Composable `AtmosphericData` (5 sub-records + `DirectionalCloudData` + `CloudApproachData`)

**Command pattern**: `ForecastCommand` → `ForecastCommandFactory` → `ForecastCommandExecutor` | `RunType` enum (VERY_SHORT_TERM, SHORT_TERM, LONG_TERM, WEATHER, TIDE, LIGHT_POLLUTION, BRIEFING, and Ask PhotoCast's `ASK` and `ASK_READY` — neither is configurable on the Models screen and both are in `defaultDateRange`'s switch; production's `job_run.run_type` is a plain `VARCHAR(20)`, so they needed no migration, but a developer's EXISTING local H2 file refuses an `ASK` row: Hibernate fixes each `@Enumerated(STRING)` column to a native H2 `enum (...)` and `ddl-auto: update` does not alter it, which `LocalH2EnumWidener` (local profile, H2 only; lives under `backend/src/local/java`, compiled only by `-Plocal-dev`, so it is not in the production jar; one line per column in its `TARGETS` registry: `job_run.run_type`, and since the evening refresh `pipeline_run.cycle_type`) widens at startup — add a line there when a change adds a value to an enum whose column an existing local database must accept) | Per-run-type model config (Haiku/Sonnet/Opus via Admin UI) | ⚠️ **Sonnet 5.5 (`EvaluationModel.SONNET_55`, `claude-sonnet-5-5`) is selectable and is not the default for any run type — but production's Batch Near-Term (T+0/T+1 sky ratings, nightly and intraday) AND Batch Far-Term (T+2, and T+3 when SETTLED) both run on it**, switched on the Models screen (Near-Term seen there 2026-10-13; Far-Term switched by the owner 2026-10-20 after `docs/engineering/same-cell-rating-spread-plan.md` measured Haiku 4.5 rating near-identical neighbours 2+ stars apart about 25 times as often as Sonnet 5.5 — the Caw Gap "rogue 4★"; the database `model_selection` row, not the code, decides this, so read the screen or the row before assuming any run type's model): it runs with the default adaptive thinking (it rejects `thinking: disabled`) at `output_config.effort = low` and a thinking-aware max-token ceiling (4096 for the sky prompt; the answer budget plus 4096 for aurora and the glosses; 16000 for the best-bet advisor) set in `ModelRequestSupport`. It is selectable on the Models screen (every run type), the Prompt Test and Sky-Rating Eval harnesses and the advisor replay, but not in `SkyRatingEvalService.SCHEDULED_MODELS` or the fixed comparison lists of the Model Test and Briefing Model Test screens. A refusal or max_tokens stop fails the evaluation for every model, and a refusal counts as a failed result for `LocationFailureService` like any other failure. On 2026-10-04 measurements (10 runs, 3 prompts) it cost about the same as Sonnet 4.6 because its tokeniser counts more input tokens, and it failed one regression case that Sonnet 4.6 passes. ⚠️ **Haiku 5.5 (`EvaluationModel.HAIKU_55`, `claude-haiku-5-5`) is selectable on exactly the same surfaces and is likewise neither the default nor active anywhere** (not in `SCHEDULED_MODELS`, the Model Test or Briefing Model Test lists, nor Ask's `photocast.ask.model`, which stays `HAIKU | SONNET`). Unlike Sonnet 5.5 it accepts `thinking: disabled`, so every request path sends thinking disabled plus `output_config.effort = low` (`ModelRequestSupport.tune`/`withThinkingSetting`/`withEffort`; the two models' rules differ on purpose and are written out in its javadoc) and keeps the Haiku answer ceilings (512 sky, no thinking allowance, since no thinking tokens count against `max_tokens`). Priced at `cost.haiku55-*` ($0.10 in / $0.50 out per MTok for prompts up to 100K tokens, cache write 1.25x / 2x, read 0.1x; above 100K the API charges 5x, which every prompt here is far below), about a tenth of Haiku 4.5, though its tokeniser counts about 30% more tokens. It rejects `budget_tokens` thinking, non-default `temperature`/`top_p`/`top_k` and assistant prefill (none is sent) and can return `stop_reason: refusal`, handled like Sonnet 5.5's. ⚠️ **It has not been run against the prompt-regression suite or the sky-rating eval**: the owner must run both (and read the veto-demotion / JSON-deliberation risks in the notes) before any run type switches to it. A local H2 file created before it existed is not widened for it (`LocalH2EnumWidener` lists `job_run.run_type` and `pipeline_run.cycle_type`, the latter added for the evening cycle), exactly as for Sonnet 5.5

The engine classes and the `optimisation_strategy` table stay until Phases 2 and 3 of `docs/engineering/sync-engine-retirement-plan.md`. **Cost tracking**: Token-based micro-dollar pricing from Anthropic SDK | `ExchangeRateService` (Frankfurter API, ECB data) | `CostCalculator` with cache/batch discount (cache writes priced by lifetime: `TokenUsage.cacheCreationOneHourTokens`, read from the API's `usage.cache_creation.ephemeral_1h_input_tokens`, is a subset of `cacheCreationInputTokens` billed at the 1-hour rate, 2x input via `CostProperties.*CacheWrite1hUsdPerMtok`; the remainder at the 5-minute 1.25x rate; no migration, `api_call_log` keeps its token columns and only `cost_micro_dollars` changed) | Frontend shows GBP + USD costs

**Job metrics**: `job_run` + `api_call_log` tables | Admin dashboard (7-day stats, per-service breakdown) | Per-location failure tracking: `LocationFailureService` settles each pipeline cycle (nightly and intraday; the evening gives no evidence, below) once, on the way to the BRIEFING phase, and counts a place's cycle once, only when it failed with no success that cycle and the places LIKE it mostly got through: for a failed Claude result, the other places with a result in the same lane (sky, woodland or bluebell; triage-only places are not evidence), for a collection error, the other places whose collection ran. At least half counts, so a fault confined to one lane or an outage that fails everything counts for nobody; any cycle in which the place got through resets the count, and a place with nothing recorded keeps it. Settles run one at a time under an in-JVM lock (single instance), each claiming its cycle with a conditional `UPDATE pipeline_run SET failures_settled_at = :now WHERE failures_settled_at IS NULL` in the same transaction as its counter writes, so a cycle is counted exactly once whatever restarts happen, and a settle that fails rolls its claim back and leaves the cycle unclaimed; the count is incremented by the database. ⚠️ **A settle has two modes, chosen by trigger order, and only one of them counts.** `FULL` counts failures and applies resets; `RESETS_ONLY` applies only the resets from successes and triage and counts nothing. A cycle is settled `FULL` only when it is settled at its own tail AND its `trigger_time` is newer than the newest settled `trigger_time` (read from the database); every later-settled cycle (an older cycle after a newer one, a replay after a failed settle, one recovered at startup or by the sweep) is settled `RESETS_ONLY` and then claimed, the mode and why logged at INFO. Counters only mean something in trigger order, since applying an older cycle's failure after a newer cycle's success could restart a streak that success had broken, but that older cycle's successes are still true, so they still reset. ⚠️ **A failed settle is retried durably by a sweep** (`LocationFailureService.sweepUnsettledRuns`): the orchestrator logs a settle failure at ERROR and completes the run anyway, so the cycle is COMPLETED with `failures_settled_at` null, and startup resumes only RUNNING runs. The sweep runs at application startup (after `resumeRunningCyclesOnStartup`) and at the start of every tail settle, under the same lock, finds pipeline runs with `failures_settled_at IS NULL` triggered within the last 7 days (`SWEEP_WINDOW`) and not still RUNNING, and settles each in trigger order, `RESETS_ONLY`; a run that fails again is logged at ERROR and left for the next sweep. ⚠️ **A run with a FORECAST batch still polling is never claimed, by the sweep or by a tail settle**: a run restarted during `FORECAST_BATCH_SUBMIT` is marked FAILED, yet its persisted `SUBMITTED` batches are still polled and can write results for hours (the Batch API's ceiling is 24 h), so claiming it at once would settle it with no result evidence and the later successes could never reset a counter. Any FORECAST batch outside `ForecastBatchEntity.BatchStatus.TERMINAL` (every status the poller stops polling: COMPLETED, FAILED, EXPIRED, CANCELLED) defers the run (INFO, naming the batch) and leaves it unclaimed for a later sweep, which the 7-day window covers; AURORA batches are ignored, as the outcome resolver reads only FORECAST batches. ⚠️ **A tail settle is FULL only if there is no older unsettled cycle within the sweep window at all, whatever its status** (one the sweep deferred for a polling batch, one it failed to settle, one still RUNNING such as the nightly in WAIT while an intraday Run now finishes first, or a listing failure that cannot rule one out; RUNNING runs are not settled by the sweep but still block): otherwise a newer failure could take a place from 2 to 3 and disable it before the older cycle's success lands, and a RESETS_ONLY sweep cannot undo a disable. Such a tail settles RESETS_ONLY (INFO "older cycle N (STATUS) still unresolved") and its cycle is never counted later, the safe direction. ⚠️ **A cycle type that gives no failure evidence (`CycleType.failureEvidence()` NONE, today only EVENING) is claimed with nothing applied** (no counts, no resets) before the polling-batch deferral, so it is never left for a sweep to retry; it is never an unresolved-older blocker for a later FULL settle; and the newest-settled-`trigger_time` rule (`findNewestSettledTriggerTime(Collection<CycleType>)`) counts only evidence-giving types, so an evening run neither demotes a late afternoon to RESETS_ONLY nor blocks the overnight's counting (evening refresh E-D5). The first deploy of V163 leaves every recent run unsettled, and the first sweep over them is harmless (RESETS_ONLY only zeroes counters, which are all zero then). The third consecutive counted failure sets `enabled = false` plus a fixed-shape `disabled_reason` and emails the admins through `AdminAlertService` after the settle transaction commits; if more than 5 places qualify in one cycle (`MAX_DISABLED_PER_CYCLE`) none is disabled and the admin is told something systemic is wrong. The scheduler's "Run now" on the nightly or intraday job runs the identical pipeline cycle, nothing records the trigger, and it counts like a scheduled one (three presses in a day could disable a place; an owner-accepted trade-off). A cycle that submitted no batch keeps its dispositions on an anchor job run with no `forecast_batch` row, so `pipeline_run.disposition_job_run_id` (V163) records which job run holds them, durably, written in the SAME transaction as the disposition rows (`ForecastDispositionService.persist(pipelineRunId, jobRunId, dispositions)`; a link that cannot be written rolls the rows back and is never swallowed, because a cycle with rows and no link would settle with no evidence and be claimed for good): a cycle that triaged candidates away resets those places even after a restart, and a cycle whose submissions all failed (the 2026-09-29 shape, `SUBMISSION_FAILED` rows only) counts nobody. The admin Locations alert's "Re-enable" (`PUT /api/locations/reset-failures`) clears the counters and sets `enabled` back for a place that has a `disabled_reason`, leaving a manually disabled place disabled. A place's success in a cycle is read from `api_call_log` AND from `forecast_score` rows stamped with the cycle's `pipeline_run_id` (the audit rows are best-effort and can be missing when a batch's job-run bookkeeping failed), while a FAILURE needs positive failure evidence, so a gap can only under-count. A cycle whose audit evidence is incomplete (any forecast batch with a null job run, whose results were never logged) counts no failures at all, because a failed row cannot then be shown to be the place's last word; its successes still reset. ⚠️ **The retry's `SKIPPED_TRIAGED` disposition write is not best-effort** (`BatchRetryService.recordRetryTriage`): a retried slot that triages away would otherwise keep only its precursor's failed `api_call_log` row and be counted failed although it was answered, so a failed insert escapes `submitRetry` as a `RetryEvidenceException`, `PipelineOrchestrator.retryFailedPhase` fails the RETRY_FAILED phase and rethrows, `waitAndBriefPhase` fails the run before its tail settle (no settle, no briefing for that cycle), and the unclaimed FAILED run is settled later by the sweep, `RESETS_ONLY`. ⚠️ **`locations.enabled`, `consecutive_failures`, `last_failure_at` and `disabled_reason` are `updatable = false`** and written only by column-scoped updates on `LocationRepository` (`updateEnabled`, `recordFailure`, `autoDisable`, `resetFailureCounts`, `clearFailureState`), exactly as the `app_user` settings columns are: `setX()` then `save()` on an existing row writes NONE of them (an insert still does), because an entity loaded before a settle and saved or merged after it (an admin's metadata edit, or a job that loads locations outside a transaction, waits on a remote call and merges its detached snapshot) used to rewrite the stale values and undo a committed disable. The detached writers of a few named columns use scoped updates too (`updateGridCell` for `GridCellBackfillJob` and `BriefingWeatherLoader`, `updateSkyBrightness` for `BortleEnrichmentService`), so a stale snapshot cannot rewrite an admin's edit either; only `LocationService.update` saves the whole entity, inside its transaction. `LocationEntity` is also `@DynamicUpdate`. The admin enable/disable toggle (`LocationService.setEnabled`, via `updateEnabled`) is deliberately last-writer-wins

**Resilience**: Resilience4j annotations (`resilience4j-spring-boot4`), configured under `resilience4j:` in the YAML profiles (attempts, backoff, breaker windows and the Open-Meteo rate limit differ by profile: read the block in the profile YAML rather than a figure here) and wired to predicates in `ResilienceConfig` | `@Retry` + `@CircuitBreaker` on `AnthropicApiClient.createMessage` (instance `anthropic`; `ClaudeRetryPredicate` retries HTTP 500, 529 and the intermittent content-filter 400) | `@Retry` + `@CircuitBreaker` + `@RateLimiter` on `OpenMeteoClient` (instance `open-meteo`; `TransientHttpErrorPredicate` retries 5xx only, deliberately NOT 429, which the rate limiter handles) | `OpenMeteoClient`'s briefing-grade calls (and `MarineClient`) use a second instance, `open-meteo-briefing`, which has no retry predicate of its own: the prod profile sets it to `maxAttempts: 1`, the local and example profiles do not configure it, so it runs on Resilience4j defaults | `@Bulkhead` on `ForecastService`: `claude` on `evaluateAndPersist` (6 concurrent calls, 120 s wait) and `forecast` on `runForecasts` (8 concurrent, 120 s wait); the same in every committed profile | Ask PhotoCast's own door, `AnthropicApiClient.createAskMessage`, runs on its own instances named `ask` (declared in all four YAML sets and read back by a test): `@Retry` 2 attempts / 500 ms on `AskRetryPredicate` (any 5xx incl. 529 on an `AnthropicServiceException` — `TransientHttpErrorPredicate` is written for Spring's exception and never matches an SDK error; no content-filter retry, no 429, no I/O), its own `@CircuitBreaker` (`registerHealthIndicator: false`; `AskBreakerIgnorePredicate` ignores a rejected key and a full bulkhead, which are load or configuration, not an outage), and `@Bulkhead` 4 concurrent / 2 s wait, so a reader can never open the shared `anthropic` breaker against the forecast pipeline; ⚠️ the SDK client behind it has its own retries OFF (`withOptions(maxRetries(0))`, as `AnthropicBatchClient` does) — the shared client retries twice with the full timeout each, which would multiply under the `ask` retry | Anthropic Batch API creation has its own slower `anthropic-batch` retry (`BatchSubmitRetryPredicate`), run programmatically from `AnthropicBatchClient` | Spring's own `@Retryable`/`@ConcurrencyLimit` are used nowhere | Dead-letter mechanism | `RequestLoggingInterceptor` | SSE auto-reconnect after backend restart

**Batch cache primer** (`photocast.batch.cache-primer.*`, `BatchCachePrimer`): before the scheduled cycle's `submitBuckets` submits anything, it submits ONE one-request primer batch per distinct sky cache prefix (model id plus coastal-or-inland prompt builder, keyed over every SKY task of the near/far inland/coastal buckets; woodland and bluebell get none) and waits for them to end, at most `wait-seconds` in total (default 180, 0 means do not prime, bounds 0..600; `poll-seconds` default 10, bounds 1..60; out-of-range values fail startup). Measured on 2026-10-04 against the live API: a cold batch of 12 gave 1 cache read and 11 writes, an ordinary warm-up call first still gave 4 and 8 (a standard call's cache is not reliably picked up by a batch), a primer batch first with a 1-hour lifetime gave 12 and 0; in production near-term sky, 23% of calls wrote the cache and those writes were 46% of the bill. ⚠️ **The 1-hour lifetime follows the primer's RESULT, never the flag.** A 1-hour write costs 2x input against 1.25x, so a real SKY request carries the 1-hour `ttl` only when it is in the scheduled cycle AND the primer for its own prefix ended with a succeeded request: `prime` returns the warmed prefix keys, `ScheduledBatchEvaluationService` hands them to `EvaluationService.submitWarmed`, and `BatchRequestFactory.buildForecastRequestAndPrompt(..., warmedPrefixes)` applies the ttl per request. Every other case (flag off, `wait-seconds` 0, primer failed, timed out, status unreadable at the deadline, interrupted, and every non-scheduled path: force-submit, JFDI, region-filtered, retry) sends the request byte-identical to what was sent before the primer existed (5-minute default); the factory has no global switch, the eval harness, woodland, bluebell and the synchronous strategy are untouched. ⚠️ **Fail-open and bounded.** Nothing the primer does may fail the cycle: the deadline is checked before every create and every read, each call has a short (15 s, or the time left) timeout, an unreadable status read counts as still pending (counted in the cycle's INFO line) rather than failing the primer, and an interrupt stops waiting, restores the flag and warms nothing. The wait adds up to `wait-seconds` to the FORECAST_BATCH_SUBMIT phase, during which a restart fails the run exactly as it does today, which is why the default is short. ⚠️ **Invisible to the batch tables, and therefore to cost recording.** Primers go straight through `AnthropicBatchClient.createPrimerBatch` (one attempt, no retry, no creation lock), never `BatchSubmissionService`, so no `forecast_batch`, `job_run`, `api_call_log` or disposition row exists for one and the pollers, result processor, retry service and `LocationFailureService` never see it. That also means its own cost (one full request per prefix per cycle, with a 1-hour cache write) is not recorded, so recorded cost under-counts by that much; a real request's own 1-hour write IS priced correctly (`CostCalculator` splits cache writes by lifetime, see Cost tracking). Its custom id (`pw-n`) is rejected by `CustomIdFactory.parse`. ⚠️ **A primer can never be adopted by a real submission, with one stated residual.** `createPrimerBatch` takes the same `creationLock` as `createBatch` (acquired with a timeout inside the primer's own deadline: if a long real submission holds it the primer is skipped, WARN, prefix not warmed), and adoption only ever runs inside that lock, so no real retry can look for candidates while a primer create is in flight, and a successful primer's id is recorded as handed out before the lock is released. For an ambiguous create (it threw, yet Anthropic may have made the batch) the attempt's window (its start to 60 s after the failure) is recorded and `findAdoptableBatch` ignores any one-request batch created inside it; no real create from this JVM can fall in that window because the primer held the lock. Residual: the window is judged on Anthropic's `createdAt` against this clock with no skew tolerance, so a primer batch created more than 60 s after the client gave up would escape it; and a real one-request batch genuinely orphaned inside the window after an ambiguous primer failure is not adopted, so its retry creates a duplicate (paid, untracked: the direction `AnthropicBatchClient` already prefers over adopting the wrong batch). Another JVM sharing the API key shares none of this. ⚠️ **Every logged Claude call now carries the API's cache diagnostics (V168, 2026-10-07), so the 2026-10-04 question can be answered per request.** `api_call_log.cache_diagnostics TEXT NULL` holds `CacheDiagnostics` as compact JSON (`{"status":"MISS","reason":"messages_changed","missedInputTokens":1234}`; `{"status":"PENDING"}` for a comparison the API had not finished; absent fields omitted), kept beside `TokenUsage` and never folded into it (the cost maths read the token counts alone). Every site that logs a `Message` passes it through: the batch result processor's forecast and aurora rows (success and the refusal/truncation rows), the synchronous engine and strategy, the glosses, the best-bet advisor and the Ask engine's turns. It is NULL for a failed call, a non-message call, a response that carried none and every row before V168. The admin Job Runs detail shows a "Prompt-cache diagnostics" section (a tally by reason and a badge per call, `cache: read 4,726 · miss — messages_changed`) only when a run has any. ⚠️ **The API reports nothing unless the request names a previous message to compare against.** `diagnostics: {previous_message_id: null}` only opts in (the API keeps a hash fingerprint of the request under the response id) and its own response is always empty; a LATER request must pass that id as `previous_message_id`, and the response then says where it diverged (`model_changed`, `system_changed`, `tools_changed`, `messages_changed`, each with an estimate of the input tokens after the divergence; or `previous_message_not_found` / `unavailable`; a comparison that found no divergence is reported as nothing). So a plain request can never produce a diagnostic, and the request side is deliberately switched OFF (`photocast.batch.cache-primer.diagnostics`, default `false`): the one real chain this pipeline has is primer to warmed batch request, and the field is in the SDK's batch request schema (`BatchCreateParams.Request.Params.diagnostics`) and documented GA, but nothing here has sent it to the live Batch API, and a rejected create would fail the whole cycle's submission. With it on, the primer's request opts in (null id), `BatchCachePrimer` publishes each ended primer's message id to `PrimerMessageIds`, and every WARMED real sky request carries `previous_message_id` = its primer's id (no id read, no diagnostics; every other request is untouched). Flip it after a one-request check; the first cycle's primer line and the first diagnosed rows show whether it works. **Whatever the flag says, the primer now reads its own result** (`AnthropicBatchClient.readFirstSucceededMessage`, one extra results call per ended primer, fail-open, inside the wait cap) and puts it on the cycle's INFO line: `cache results: {<prefix>=msg_… wrote N tokens (M at 1h), read R, diagnostics …}`, which answers "did the primer's one-hour write land" from the logs (a primer is the first turn, so its own diagnostics read `none`). Still unlogged to `api_call_log`: the primer's calls. Not opted in anywhere else: the synchronous strategy, aurora, the glosses and the advisor are single-shot (no previous message to name), and the Ask engine, the one multi-turn caller, could chain each turn to the last response id (not built). **Reading a row:** `messages_changed` ALONE is the healthy answer for a primed request (model, system and tools matched the primer; only the user message differs); `system_changed`, `tools_changed` or `model_changed` means the prefix really differs from what the primer cached; `previous_message_not_found` means the fingerprint expired or the primer did not opt in; `unavailable` or `PENDING` is no answer. **The query** (portable SQL, run on H2 in `ApiCallLogCacheDiagnosticsPersistenceTest` and on Postgres in `ApiCallLogCacheDiagnosticsMigrationTest`; there is no `request_url` on a batch row, so a batch row is `is_batch = TRUE`): `SELECT batch_id, COUNT(*) AS calls, SUM(CASE WHEN cache_read_input_tokens > 0 THEN 1 ELSE 0 END) AS calls_that_read, SUM(cache_read_input_tokens) AS read_tokens, SUM(cache_creation_input_tokens) AS write_tokens, SUM(CASE WHEN cache_diagnostics IS NULL THEN 0 ELSE 1 END) AS with_diagnostics, SUM(CASE WHEN cache_diagnostics LIKE '%"reason":"messages_changed"%' THEN 1 ELSE 0 END) AS only_messages_differ, SUM(CASE WHEN cache_diagnostics LIKE '%"reason":"system_changed"%' OR cache_diagnostics LIKE '%"reason":"tools_changed"%' OR cache_diagnostics LIKE '%"reason":"model_changed"%' THEN 1 ELSE 0 END) AS prefix_changed, SUM(CASE WHEN cache_diagnostics LIKE '%"reason":"previous_message_not_found"%' OR cache_diagnostics LIKE '%"reason":"unavailable"%' THEN 1 ELSE 0 END) AS no_comparison FROM api_call_log WHERE service = 'ANTHROPIC' AND is_batch = TRUE AND succeeded = TRUE AND called_at >= '<first cycle after enabling>' GROUP BY batch_id ORDER BY MIN(called_at), batch_id`. `calls_that_read` against `write_tokens` is the 2026-10-04 read-versus-write question per batch; the other columns say why a call did not read.
