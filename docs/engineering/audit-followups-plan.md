## T — token hardening (no migration)
**(a) Rotate at verify, by compare-and-set.** `RegistrationService.verifyEmail` (`:165-182`) today
reads, checks and saves with no lock. New: after the checks, one conditional update
`UPDATE email_verification_token SET token_hash=:new, verified=true, expires_at=:exp
WHERE id=:id AND token_hash=:old AND verified=false` with `exp = min(old expiry, now + 30 min)`; one row
→ return the fresh raw value as `setupToken`; zero rows → "This link has already been used — sign in or
request a new one" (this replaces today's "Invalid verification token" for a not-found token too;
existing assertions change). `POST /api/auth/set-password` is unchanged and now only accepts the rotated
value. Frontend: `RegisterPage` keeps `setupToken` in React state only (never storage or the URL) and
ignores a late verify failure once it is in SET_PASSWORD (StrictMode double-fires the verify effect in
dev, `main.jsx:13-16`; a double click does in prod).
**(b) Revoke at logout.** New `AuthenticationService.logout(rawRefresh, principal)` (not in the
controller): identify the user from an **unrevoked, unexpired** refresh token, else an authenticated,
non-anonymous Bearer principal (`authenticatedUsername()`); in one transaction `lockAccount` (parent
first, matching `TokenIssuer.rotate`), revoke the presented refresh with the existing conditional
`RefreshTokenRepository.revokeIfActive(hash)`, then a new column-scoped
`AppUserRepository.bumpCredentialsVersion(id)` (**not** `applyCredentialChange`: no
`credentials_changed_at` stamp, so replay detection still reads `REVOKED_SEEN`).
**Client order matters:** `AuthContext.logout` (`:82-91`) must capture the refresh token, then clear
localStorage and in-memory tokens, **then** await `apiLogout`; otherwise a 401 in the window makes
`axiosClient` (`:92-135`) post `/refresh` with the revoked token, which `TokenIssuer` classifies
`REVOKED_SEEN` and family-revokes every device.
- Effect: every outstanding access token of the user dies at its next request; other devices take one
  silent refresh; an open SSE stream is cut only at reconnect (documented).
- Ship backend and frontend together (one release; an old cached SPA fails set-password once).
- Tests: `RegistrationServiceTest` (rotation; second verify after rotation → already used; set-password
  with the mailed token fails, with the setup token succeeds; 30-minute expiry), `AuthControllerTest`,
  `AuthenticationServiceTest` (logout bumps `cv`; other refresh tokens survive; an expired refresh does
  not bump; replay classification unchanged), `TokenIssuerTest`, `CredentialInvalidationFlowTest`,
  `RegisterPage.test.jsx` (double-fired verify), `RegisterPageHome.test.jsx`, `authApi.test.js`,
  `App.test.jsx`, `AuthContext.test.jsx` (storage cleared before the POST resolves),
  `axiosClientRefreshCycle.test.js` (a 401 during logout posts no `/refresh`).
- Docs in T's PR: `token-log-redaction-plan.md` §4 (status). Shared docs go to Z.

## D — dormant account job (migration)
- **Migration:** `app_user.dormancy_warning_sent_at TIMESTAMP` (nullable; entity `insertable=false,
  updatable=false`, written only by scoped updates); seed `scheduler_job_config` row
  `dormant_account_sweep`, CRON `'0 15 10 * * *'`, **status PAUSED** (template: V184).
- **Properties** (`@Component @ConfigurationProperties("photocast.dormancy")`, `RegistrationProperties`
  pattern; defaults are **Java field initialisers**, not yml): `dryRun = true`, `inactiveDays = 90`
  (`@Min(30)`), `graceDays = 14` (`@Min(7)`). Add the keys to `application-example.yml` and
  `reference/configuration.md`.
- **The locks, stated exactly:** the schedule runs only when the row is resumed; **"Run now"
  (`triggerNow`) runs it even while PAUSED**, so nothing is sent or deleted unless `dryRun` is false.
  This job's `triggerNow` logs the acting admin's username.
- **Who:** `role = LITE_USER` only (never ADMIN, never PRO_USER), `enabled = true`, not pending, a
  non-blank email. Inactivity is `COALESCE(last_active_at, created_at)` against
  `Clock.systemDefaultZone()` (both are JVM-zone `LocalDateTime`s). An admin-created account that never
  signs in is warned at `created_at + 90` days (intended).
- **Warn — send first, stamp after.** For a candidate inactive ≥ `inactiveDays` with no warning since its
  last activity: send `dormancy-warning-email` (html with the email-brand fragments + `templates/text`
  txt; synchronous `sendDormancyWarningEmail` returning a boolean, like the reminder); **only if the
  sender accepted it**, stamp `dormancy_warning_sent_at` with a conditional update. A crash before the
  stamp leaves the account unwarned (it is retried next run); a duplicate warning from overlapping runs is
  harmless. Never warn or delete when no mail sender is configured.
- **Delete:** warning stamped ≥ `graceDays` ago and no activity since it. `UserService.purgeDormant`
  copies `purgeAbandonedPending` and the `deleteOwnAccountIfUnchanged` compare-and-set: lock the row,
  re-check **role = LITE_USER, enabled, non-blank email, inactivity and the warning stamp** both in the
  locked read and in the conditional delete's WHERE (a promotion, disable or sign-in in between saves the
  account), `purgeUserRows`, release the email claim; after commit send the account-deleted email.
- **Dry run** reports per run: would-warn count, would-delete count, and for warned-in-dry-run accounts
  "deletable from <date>" (a dry run stamps nothing, so deletions are projected).
- **Logs:** ids only — the warning send and the dormant path's deleted-email log no address or username
  (DEBUG at most); one INFO tally per run.
- Tests: copy `PendingRegistrationSweepJobTest` (fixed `Clock`; dry run sends and deletes nothing and
  reports the projection; Pro, Admin, disabled, pending and no-email accounts never touched; a sign-in, a
  promotion or a disable after the warning cancels deletion; a failed send stamps nothing; a crash between
  send and stamp leaves the account unwarned), purge tests like `UserServicePurgeAbandonedTest`,
  `UserEmailServiceTest` (the new send; JaCoCo is 80% per class), the two email-template list tests, a
  properties validation test (`@Min`), a CI migration test like `PendingRegistrationRemindersMigrationTest`
  (row seeded PAUSED, column present); `AccountDeletionIntegrationTest` covers the FKs.
- Docs in D's PR: `reference/configuration.md`, `reference/dev-and-testing.md` (local H2 has no job row).
  Shared docs go to Z.

## W — waitlist invites and hardening (migration)
- **Migration:** `waitlist_email` gains `invite_token_hash VARCHAR(64) UNIQUE`, `invited_at TIMESTAMP`,
  `invite_expires_at TIMESTAMP`, `invite_used_at TIMESTAMP` (entity `insertable=false, updatable=false`,
  scoped updates only).
- **A new `WaitlistService`** holds the logic (the controller today holds it, `WaitlistController:30-46`).
- **Invite:** `POST /api/admin/waitlist/{id}/invite` (ADMIN) refuses a non-ASCII address (register
  rejects those, `AuthController:268`), mints a random token, stores its hash, `invited_at`, a 7-day
  expiry, clears `invite_used_at`, and mails `waitlist-invite-email` (html + txt) linking
  `<app>/register#invite=<raw>` via a new `UserEmailService` invite-link builder (`appLink` builds
  `#token=`, which `App.jsx` treats as a verification link). Re-inviting replaces the token.
- **Routing the link:** lift `#invite=` in `main.jsx` beside `takeLinkToken()` (out of the address bar
  before render), and make `AuthGate` (`App.jsx:81-155`) open `RegisterPage` with an `inviteToken` prop
  when one is present (signed-out); a signed-in browser ignores it.
- **Register with an invite:** `POST /api/auth/register` accepts optional `inviteToken`. Valid means a
  conditional update `SET invite_used_at = now WHERE invite_token_hash = :h AND invite_expires_at > now
  AND invite_used_at IS NULL AND lower(email) = lower(:requestEmail)` returning 1; then
  `RegistrationService.register` skips the **cap** check (not `registration.enabled=false`, which still
  refuses). Turnstile still applies, strictly. Anything else takes the normal cap path and the same 403
  (no leak). The waitlist row is **deleted at activation** (set-password), not at register, so an
  invitee who never verifies keeps their place; the email claim already stops two accounts per address.
- **Admin delete:** `DELETE /api/admin/waitlist/{id}` (ADMIN), replacing manual SQL.
- **Hardening `POST /api/waitlist`:** strict Turnstile (a second `TurnstileWidget` on the waitlist step;
  the register token is already spent; the two never mount together); `AuthAttemptLimiter` bounds per
  client address plus a global hourly cap, which answers **429** (not a silent 200); catch the
  unique-constraint race and answer the same 200; log an id, not the address. (`ClientAddress` trusts
  `CF-Connecting-IP`/first `X-Forwarded-For`; the global cap is the backstop if the origin is reached
  directly.)
- **Frontend:** `RegisterPage` sends the invite token; the waitlist step's copy becomes "we'll email you
  an invitation when a place opens"; `WaitlistManagementView` gains Invite and Remove buttons and an
  "Invited <date> · expires <date>" state; `WaitlistEntryDto` gains `invitedAt`, `inviteExpiresAt`
  (never the hash); `waitlistApi` gains the two calls.
- Tests: `WaitlistServiceTest`, `WaitlistControllerTest` (Turnstile, 429, duplicate race),
  `WaitlistAdminControllerTest` (Lite and Pro 403; Admin 200; JSON has no hash), `AuthControllerTest`,
  `RegistrationServiceTest` (the invite bypasses the cap only for the matching email, once; expired, used
  or mismatched falls back to the cap; `registration.enabled=false` still refuses), activation deletes
  the row, the email-template lists, `UserEmailServiceTest`, `WaitlistManagementView.test.jsx`,
  `ManageViewWaitlist.test.jsx`, `RegisterPage.test.jsx`, `App.test.jsx` (invite link signed out and
  signed in), `authApi.test.js`, a CI migration test.
- Docs in W's PR: `reference/api-endpoints.md` (the waitlist routes). Shared docs go to Z.
