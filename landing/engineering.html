The engineering
behind PhotoCast.

PhotoCast is a full-stack forecasting service that I design, build and run on my own, drawing on more than 25 years of software engineering. This page is for engineers: the stack, the pipeline every change goes through, the gates it has to pass, and where it still falls short. The figures are the ones enforced in the build today.

At a glance

  • Java 25 and Spring Boot 4 on the server, React 19 in the browser, PostgreSQL underneath.
  • Four required checks on every pull request, including per-class coverage, static analysis and dependency scanning.
  • A tagged release builds, backs up, deploys and health-checks itself.
  • Claude rates the sky and answers questions, and the model is tested every week against real outcomes.
  • I own the design, the plans, every review decision and every release.

The stack

  • Backend: Java 25 and Spring Boot 4: a REST API with Spring Security and JWT authentication, Spring Data JPA, Flyway migrations (more than 200 so far) and PostgreSQL in production. Virtual threads for the I/O-heavy forecast runs, and declarative HTTP clients for the weather service.
  • Frontend: React 19, Vite and Tailwind, with Leaflet for the map. The frontend is deliberately a render layer: verdicts and picks are decided on the server, and the few things the client works out for itself are a named, reviewed list.
  • AI: Claude, through the Anthropic Java SDK, rates the sky and powers Ask PhotoCast.
  • Data sources: Open-Meteo weather and air quality, WorldTides, space-weather feeds, and postcode, routing and light-pollution services.
  • Delivery: GitHub Actions, and Docker images built from each tagged release.

Continuous integration

Every pull request goes through the same checks, whoever or whatever wrote it. Four are required by branch protection on main, so a change can't be merged while one is failing:

  • Backend: build, test and coverage. mvn clean verify, which compiles, runs Checkstyle, the unit tests and the integration tests, then enforces the coverage gate and SpotBugs. On pull requests it also checks that the lines the change touches are covered. The integration tests use Testcontainers to start a real PostgreSQL, so every database migration is proven on the same engine as production before it's merged.
  • Frontend: lint, test and build. ESLint (including accessibility rules), Vitest with overall, per-file and changed-lines coverage floors, npm audit at high severity, the production build, a check that the map library stays out of the first page load, and nginx -t on the web server's config, because nothing else would catch a broken config before production.
  • CodeQL static analysis, for Java and JavaScript.
  • OWASP Dependency-Check on the server's libraries. It scans when a change touches them, and otherwise reports a pass so the requirement can always be met.

Shell scripts are checked with ShellCheck as well. A pull request that only changes documentation skips the expensive steps, but every required check still reports, so nothing merges unchecked.

Per-class coverage is the one I'd defend hardest. An overall average lets a well-tested utility package hide an untested service; per class, a new class can't lean on the rest of the codebase for its number. The lines a change touches must be covered too, on the server and in the app, and every app file has its own floor.

Security and the OWASP Top 10

I use the OWASP Top 10 (2025) as a checklist rather than a badge. Where the checks above fit it:

  • Software Supply Chain Failures. OWASP Dependency-Check on the server's libraries and npm audit on the app's, both blocking on serious findings. Dependabot proposes updates weekly; minor and patch updates merge once the required checks pass, larger ones are reviewed by hand, and either way they reach the live service only with the next release, which I make by hand.
  • Injection. CodeQL and FindSecBugs on every change, and CodeQL again weekly so new rules also look at code that hasn't changed. Database access goes through JPA and parameterised queries; there's no SQL built from strings.
  • Broken Access Control. Every admin-only endpoint carries a server-side role check, and everything under the admin API is also refused by Spring Security's filter chain before a controller sees it. Pro features are enforced by a 403 on the server; hiding a button is never the control.
  • Security Misconfiguration. The app sets a Content Security Policy that disallows inline styles, and the web server's config is syntax-checked on every change.

Beyond the checklist

  • Dynamic testing. Every week OWASP ZAP signs in as a test account and runs an active scan of the API from its OpenAPI definition, against a temporary copy of the service, plus a baseline scan of the app. A gate script, not ZAP's own exit code, decides the result: any alert of Low risk or above without a written exception fails it, and so does a scan that covered less than it should.
  • Personal data stays out of shared caches. Nothing personal rides a response that's shared through HTTP caching, and a test lists the personal paths that caching must never touch.
  • Secrets stay out of logs. Links carrying one-time codes are kept out of the web server's logs, and a check confirms it.

None of this is a substitute for a professional penetration test, and I don't claim one.

Continuous delivery

  • A tag is a release. I run the release script, which folds the pending changelog entries into the changelog and tags the version. The tag starts the deploy workflow: it re-runs the full CI suite, builds the backend and frontend Docker images, publishes them to a container registry, backs up the database, deploys and checks the service came up healthy. Any failure stops the deployment and tells me.
  • Traceable. Both images are tagged with the release version, the running server reports it and the app displays it. Every change arrives as a pull request, and larger ones link to a written plan. The changelog is built from one file per change, so open pull requests don't fight over the same line.
  • Watched. A daily health check runs from inside the server and from outside it, a daily test restores the latest backup into a scratch database and counts the rows, and a daily smoke test sends a real request through the AI rating path.
  • Reversible. There's a scripted rollback to the previous release, including the database. Fixing forward is usually better; rollback is the last resort.

Testing beyond coverage

Coverage says what the tests ran, not whether they'd notice a bug. So:

  • Mutation testing. PIT runs weekly over the service and utility layers, planting small faults and checking the tests fail. The threshold is 60% of mutants killed.
  • Testing the model, not just the code. A weekly evaluation re-rates a fixed set of past sunrises and sunsets whose outcome is known, eight times each, and charts the spread over time. That catches drift when a model changes, and it decides which model runs which job: a newer model was taken off a production job after a day, when the evaluation showed it under-rating a clear-horizon morning.
  • Prompt regression tests. A larger suite checks real model output against ground truth from what was actually observed. Only I change those expectations; the AI tools that write the code are forbidden to.
  • Recorded contracts. Saved real responses from the weather, space-weather, postcode, routing and light-pollution services pin how PhotoCast parses them, and a contract test pins the JSON date format the API puts on the wire.
  • Time is injected. "Today" in the UK is derived from an injected clock everywhere, so the tests cover midnight, daylight-saving changes and a server running on UTC.

In all, more than 25,000 automated tests across the server and the app.

AI inside the product

  • Ask PhotoCast uses tool calling rather than document retrieval. It's retrieval-augmented generation (RAG), but instead of searching a pile of documents, the model queries PhotoCast's own served forecasts through tools, in a loop of at most four turns, and replies through a structured tool call rather than free text. A validator checks every pick against the live forecast before it's shown. Common questions are matched to precomputed answers by keyword rules rather than embeddings, deliberately, so behaviour is predictable and testable.
  • Prompt caching. The static part of the prompt and the tool definitions are cached across questions; only the per-question tail changes.
  • Batch processing. Scheduled forecast runs go through the Message Batches API, and which model runs which job is a database setting, so a model can be swapped or rolled back without a deploy.
  • Spend is visible. Every production model call is logged with its input, output and cache token counts, so a change in cost is something I can see, not guess.

How the code gets written

I own the design, the plans, every review decision and every release. AI models do most of the typing, under a fixed process: one model plans and reviews, and a different one writes the code in an isolated copy of the repository and has to get the full local build green before I see the change. Every pull request is then reviewed again by an AI reviewer from a different company. The plans are written down (more than 120 of them) and challenged before any code exists. How PhotoCast is built covers this in plain English.

Where it falls short

  • The app's tests run in a simulated browser. A few real-browser tests exist, but they run by hand.
  • Mutation testing covers the server only, and runs weekly rather than on every change.
  • The prompt regression suite runs by hand, because every run spends real money; the weekly evaluation fills the gap in between.
  • PhotoCast runs as Docker containers on a single Linux host, with no separate staging copy of the live service. Backups, health checks and rollback reduce the risk; they don't remove it.
  • The security checks are automated, not a professional penetration test.
