How PhotoCast
is built.

I build PhotoCast with help from AI tools, drawing on more than 25 years of software engineering experience. Those tools help with planning, writing code and reviewing changes. Automated tests, checks against observed conditions and my own release decisions help assess the results.

This page explains that process, and where it still falls short.

The short version

  • Larger features start as a written plan, which is challenged before any code is written. Smaller fixes start from a shorter brief.
  • One AI model writes the code, and separate AI reviews check it. I make the final decision on what is released, and when.
  • Whenever a code change is proposed, the automated tests and checks run, and the change can't be merged until the required ones pass.
  • A selected set of past sunrises and sunsets, whose outcome is known, is re-rated every week to see whether the forecasts have shifted.

Checking the forecast against the sky

A forecasting app is only as good as its forecasts, so some of the most important checks aren't about code at all. They test particular, well-understood cases. That is narrower than an overall accuracy figure, and none of these checks produces one, but it shows clearly when something has changed.

A weekly sky check

Every week PhotoCast re-rates a selected set of past mornings and evenings whose conditions and outcome are already known, using the same rating process as the live forecasts. Each case has an expected range of ratings rather than a single score, because a sky forecast is a judgement.

Each case is rated eight times. The AI model doesn't give exactly the same answer every time, so repeating the question shows whether a rating is steady or wandering between, say, two and four stars. The results are recorded and charted over time. That reveals drift: a change in the ratings when the model, or the way it behaves, changes.

The weekly run records results rather than blocking anything; I review the trend. When I run the same check by hand, every one of the eight ratings has to fall within the expected range for a case to pass. A different AI model is checked against these same cases before it is used for live forecasts.

Forecast regression tests

Regression tests check that a change hasn't made previously assessed cases worse. A larger set of real cases covers the full sunrise and sunset rating, the mist and night-sky forecasts, and Ask PhotoCast's answers. Each expected answer comes from what was actually observed on the day.

Only I change those expected answers. The AI tools that work on the code are instructed never to edit them, so a change can't pass by moving the goalposts.

Your ratings

Pro users can record how a past sunrise or sunset actually turned out, using "How was it?" on the map. Those ratings are compared with what PhotoCast forecast. Your feedback helps identify forecasts that were too optimistic or too cautious and provides evidence for future improvements. A rating doesn't change the forecasts by itself.

How a change is made

  1. A plan. Larger features start as a written plan that sets out what will change and why; smaller fixes start from a shorter brief. Before any code is written, reviewers are asked to challenge the assumptions, look for missing cases and identify what could go wrong.
  2. The code is written separately. A different AI model writes the code from the plan, in its own isolated copy of the project, and has to get the checks passing before the change is put forward.
  3. Separate reviews. The AI that planned the change reviews the result, and every proposed change is then reviewed by an AI reviewer from a different company. Different models can still miss the same problem, so these reviews add to the automated checks rather than replace them. Anything they find is fixed and checked again.
  4. Automated checks. GitHub Actions runs the required checks whenever a code change is proposed: the server's build and tests, the app's tests and build, a security scan of the code and, when a change touches the server's libraries, a check of those libraries for known vulnerabilities. This is continuous integration: checking that changes work together before they are merged. A change can't be merged while a required check is failing.
  5. I decide what is released. I decide what gets built, judge the results in use, and choose when a version is released, usually after the changes have been used for real.

Keeping a record

PhotoCast's code is managed in GitHub, which keeps a history of every change. Each change arrives as a pull request, which brings together the proposed code, the review comments and the automated check results before it is merged. The plans record which pull requests carried them out.

Each release has a version tag that marks exactly which code was released, the server and app built from it carry that version number, and the changelog explains what changed.

From release to the live service

A release starts with a command I run. It records the version in the changelog and tags it. The tag starts an automated workflow that runs the full checks again, builds the server and the app, backs up the database, deploys the new version and checks that it came up healthy. If any step fails, the deployment stops and I'm told.

This website is published separately, by its own script, and isn't part of that release.

The automated checks

  • Tests. More than 25,000 automated tests cover the server and the app: the forecasting rules, the maps and planning screens, the tide and aurora logic, and the small details such as which day "today" is in the UK when the server runs on a different clock. They run whenever a code change is proposed; changes to documentation and this website skip them.
  • Tests that are tested. It's possible to write tests that pass whatever the code does. Every class in the server's code must have at least 95% of its lines (the share of lines the tests run) and 90% of its branches (the different paths code can take at a decision) run by the tests, and at least 90% of the lines a change adds or alters must be covered before it can be merged. A few classes sit below these figures because their remaining paths can't happen in practice; each has its own lower minimum, with the reason written beside it. The app's code is held to the same minimum, file by file: at least 95% of its lines and 90% of its branches, and at least 90% of the lines a change adds or alters. Two app files sit a little below the branch figure for the same reason, each with its own lower minimum and the reason written beside it. Coverage shows what the tests run, not whether they check the right thing, so once a week mutation testing deliberately introduces small faults into the core forecasting code and checks that the tests notice. That weekly result doesn't block changes: if it falls below its threshold, a failure report is opened for me to investigate.
  • Recorded responses. Saved responses from the weather, space-weather, postcode, routing and light-pollution services check that PhotoCast handles known responses correctly. They can't detect a provider changing its live service. For the AI step, a daily check sends a small real request through the forecast process to confirm it still completes.
  • A test database. Changes to how data is stored are tested against a test database running the same database software as production, before they can be merged.
  • Code standards. Automated checks require written documentation on the server's public code, keep the formatting consistent, and look for common bug patterns and security mistakes. The app's code is checked for some common accessibility problems; that helps, but it doesn't establish that the app is fully accessible.

Security and your data

  • A security scan of the code runs on every proposed code change, and again every week so that new detection rules also look at code that hasn't changed.
  • The app's third-party libraries are checked for known serious vulnerabilities on every code change. The server's are checked whenever a change affects them, and again every day. A change that would bring in a library with a known serious vulnerability can't be merged, unless the problem has been looked into and doesn't apply to PhotoCast.
  • Automated tools propose library updates every week. Minor updates are merged once the required checks pass; larger ones are reviewed first. Either way, they reach the live service only with the next release.
  • Once a week, an automated scanner signs in as an ordinary user and probes a temporary copy of the service for common web vulnerabilities, working through the full list of requests the app can make to the server. Anything it finds that hasn't already been looked at opens a report for me, and so does a scan that didn't run properly or covered less than it should. Because it runs weekly, it doesn't hold up changes.
  • The app tells your browser where it may load its scripts, styles and images from (this is called a Content Security Policy), and doesn't allow styles written directly into the page. That limits what any code slipped into a page could do, though it's one safeguard among several rather than a complete defence.
  • The parts of the service only I can use are refused to everyone else before a request is dealt with, and checked again in the code behind them.
  • Personal information, such as your home postcode and settings, is never stored in the shared caches that speed up forecasts for everyone, and a test checks that it stays out.
  • Links that carry one-time codes, such as email verification links, are kept out of the web server's logs, and an automated check confirms it.

These are examples of the safeguards in place, not a complete security assessment.

This page is about the AI used to build PhotoCast. PhotoCast also uses AI within the service, to assess conditions, write its explanations and answer Ask PhotoCast questions. The FAQ and the Privacy notice explain that, including what is sent to the AI provider, and what PhotoCast stores and why.

Keeping it running

  • Built from the release. The server and the app are built from the tagged release and run in their own containers; the database runs in the standard PostgreSQL container. Each deployment takes its configuration from the same tagged version, apart from passwords and keys held on the server, so it's clear which code and settings are running.
  • When a source fails. If a weather or tide service is slow or unavailable, PhotoCast retries, then backs off rather than repeatedly sending requests. A location that fails three forecast runs in a row, while similar places get through, is switched off and I'm alerted, so it doesn't hold up the rest. If many places fail at once, which points to a wider problem, none is switched off and I'm alerted instead.
  • A watchdog. If a forecast run doesn't start on time, or hasn't finished as sunrise or sunset approaches, an email alert is sent.
  • Daily health checks. Every day, automated checks look at the server's own services and confirm that the public app can be reached from outside. The same checks run after every release.
  • Backups that are tested. The database is backed up every night, with a copy kept away from the server. Every morning the latest backup is restored into a separate scratch database and checked, because a backup is only useful if it can be restored. A further backup is taken just before each release.
  • A way back. If a release goes wrong, there is a procedure to return to the previous version. It also restores the database to how it was before the release, so anything recorded since would be lost. Fixing forward is usually better; rollback is the last resort.

Where it's still improving

Being honest about the gaps is part of the same standard.

  • The app's tests run in a simulated browser: a program that imitates a web page, so the tests run quickly without opening one. A few tests in real browsers exist, but they're run by hand rather than on every change.
  • The server's tests are checked by mutation testing and a strict coverage minimum, class by class and for every change. The app's tests have the same strict coverage minimum, file by file and for every change, but not mutation testing yet.
  • The larger forecast regression suite is run by hand rather than on every change, because each run uses paid AI requests. The weekly sky check provides an additional regular check in between.
  • PhotoCast runs on a single server, without a separate test copy of the live service. Backups, health checks and rollback help reduce the risk, but a single-server failure can still interrupt the service.

PhotoCast cannot remove the uncertainty from a sunrise or sunset forecast. These checks help catch software mistakes and identify where the forecasts need to improve. When something goes wrong, the aim is to understand why and use that evidence to make PhotoCast better.
